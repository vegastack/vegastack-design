Every page in a [`Shell`](/docs/components/shell) is one `ShellPage`, and it has **one of four
widths**. Every page shares **one gutter**, so their
edges line up. Which width a route
gets is declared **once**, in a route map the page, its loading skeleton and a test all read.
Nothing else decides a page's width or gutter.

<PageLayoutSpecimen />

## The four widths

| `size`    | Width                          | Use it for                                                           |
| --------- | ------------------------------ | -------------------------------------------------------------------- |
| `prose`   | 720px of content, centred      | A profile, a reading page                                            |
| `form`    | 720px of content, centred      | Settings and forms — `ShellPage` spaces their sections further apart |
| `default` | Up to 1200px, centred          | Lists, dashboards, record pages, a home page                         |
| `full`    | Edge to edge, fills the height | Boards, canvases, chat — a surface that uses the whole content area  |

`default` is the default.

```tsx
<ShellMain>
  <ShellPage size="prose">
    <PageHeader title="Profile" />
    <ProfileForm />
  </ShellPage>
</ShellMain>
```

The widths are caps on the **content area** — the space between the rail and column and the
panel — not on the viewport. Folding the column or opening the panel changes the room a page has,
not its width: a `prose` or
`default` page stays put and centred until the area is narrower than it, and a `full` page grows
and shrinks with the area. Grids inside a page answer to the content area too, through
`ShellMain`'s `@container/shell-content` queries.

## The gutter

One CSS variable, `--page-gutter`, pads the page on every side. `ShellPage` sets it by the
content area's own width (a container query), so it follows the room the page has, not the
window:

| Content area  | `--page-gutter` |
| ------------- | --------------- |
| Below 640px   | 16px            |
| 640px–1023px  | 24px            |
| 1024px–1919px | 32px            |
| 1920px up     | 48px            |

`ShellBleed` takes a grid or canvas past the gutter to the page's edges, and `ShellSection` gives a
region of a page its own measure — both without a width class of their own.

## Small screens

- **Phone** — the rail gives way to the bottom bar and the column opens as a sheet, so the page
  has the whole width. The gutter steps to 16px.
- **Record pages** — the work runs in one main column; reference material (Details, Related,
  Files, Attendees…) stacks in `RecordLayout`'s one side panel, flush to the page's right edge:
  docked from 1088px of record width, floating over the page below that, a bottom sheet from a "Details" button on
  a phone — never a rail of cards inside the page. From a list, a record opens in a `Peek`.
- **Boards** — a `full` page keeps its horizontal scroll inside the board, never on the page.
- **One vertical scroller** — the shell's content area. A record layout or a fill board takes
  exactly the height left, so the page never scrolls under it ([Scrolling](/docs/foundations/scrolling)).

## One route map

Declare every route's width once with `definePageWidths` from the `page-layout` lib
(`shadcn add @vegastack/page-layout`). Keys are the app's route
patterns in Next.js spelling, without route groups.

```ts title="lib/page-widths.ts"
import { definePageWidths } from "@/lib/page-layout";

export const pageWidths = definePageWidths({
  "/": "default",
  "/tasks": "default",
  "/tasks/[taskId]": "default",
  "/settings/profile": "prose",
  "/products/new/[[...step]]": "prose",
  "/ask": "full",
});
```

- **The page** passes the literal: `<ShellPage size="prose">`.
- **The loading skeleton** reads the same map from the pathname, so it paints at the page's
  width: `<ShellPage size={pageWidths.widthOfPath(usePathname())}>`. `widthOfPath` resolves a
  pathname to the most specific listed route, the way Next.js does — `/tasks/new` beats
  `/tasks/[taskId]`.
- **A test** walks every `page.tsx`, turns its folder into a route, and checks that the map lists
  it and that the page's `ShellPage` says the same `size`. An exhaustive map is what makes that
  check, and `widthOfPath`, exact.

A page whose width changes with its own state — a task list that switches to a board — passes the
state's width (`size={board ? "full" : "default"}`); the map holds its resting width.

## Guardrails

- `vegastack-design doctor` fails on a `ShellPage` carrying a `max-w-*`, `w-*`, `mx-*` or
  padding class (`p-*`, `px-*`, `py-*`, `pt-*`, `ps-*`, `pe-*`) — the page choosing its own width or gutter.
  `pb-*` stays legal: room for a docked save bar is not a gutter.
- It also compares each `ShellPage` in an App Router `page` or `layout` file with the route
  map: the `"/route": "prose" | "form" | "default" | "full"` rows of a `definePageWidths(…)` call, plus any
  `widths: { … }` object that feeds the map (a module registry listing its own routes). Route
  groups and parallel slots are stripped, the most specific row wins, a route the map does not
  list is `default`, and a layout answers for every page in its folder. A literal `size` (or none, which is `default`) that disagrees is a warning, a
  failure under `--strict`. A `size={…}` expression is skipped and counted, a `ShellPage`
  outside a route file is out of scope, and with no route map the check says so and passes.
- Don't wrap a page's content in a `max-w-*` or padded `div` either; if a section needs to be
  narrower than its page, the page has the wrong width.
