building something that will be **handed to a client**, read
[Client projects](/docs/guides/external-projects) instead — the delivery model differs.

## Setup

Follow the [Quickstart](/docs/guides/quickstart) — internal projects use the full path:
public npm packages + the private registry with the shared service token
([Registry access & auth](/docs/guides/registry-auth)).

## How updates reach you — the two-speed model

Every design-system change arrives through exactly one of two channels, and they behave
in opposite ways. Knowing which is which tells you what a release means for your app.

### Channel 1 — npm: global, semi-automatic

`@vegastack/design` (+ `@vegastack/design-tokens`) are ordinary npm dependencies. You get
changes when you bump the package — Renovate/Dependabot makes this near-automatic.
**Nothing changes until you bump** (the lockfile pins you).

What travels this channel: **token values** (colors, radius, spacing, motion), the
**base a11y layer**, the `cn()` merge configuration, the icon runtime, the preset, the CLI.

The consequence: a token change **repaints your entire app at the next routine dep
bump** — no component re-pull needed, because your copied components only reference
semantic utilities. That's the system's "restyle every app with one publish" lever.

### Channel 2 — registry: frozen, explicit, reviewed

Your components are **copies in your repo**. A registry release changes nothing for you
until you act:

```bash
pnpm exec vegastack-design check-updates          # what moved upstream
pnpm dlx shadcn@latest add @vegastack/<name> --diff       # read the change
pnpm dlx shadcn@latest add @vegastack/<name> --overwrite  # take it
```

This covers component markup changes, behavior fixes, **and API changes** — an API break
surfaces as *your* typecheck failing after the pull, never as silent runtime breakage.
The [Changelog](/docs/changelog)'s `⚠️ Breaking` section flags these ahead of time.
Blocks (`dashboard-01`) go further: never update-tracked — your adaptation is yours.

### The propagation matrix

| Design-system change | How it reaches you | Speed | Review point |
| --- | --- | --- | --- |
| Token values / base.css | npm bump | fast, app-wide | the DS's own VRT + contrast gates |
| `cn()` merge config | npm bump | fast, subtle | changelog entry |
| Component markup (aesthetic) | pull + `--diff` | per-component | you read the diff |
| Component behavior / bugfix | pull + `--diff` | per-component | your smoke tests |
| API / breaking | pull + `--diff` | per-component | your typecheck + `⚠️ Breaking` |
| Removed / renamed item | never (copies are self-contained) | — | changelog mapping |
| New component / block | opt-in `shadcn add` | — | — |

### The cross-channel ordering trap

When a component update **uses a newly added token**, the channels must land in order:
**npm bump first, component re-pull second.** Reversed, the pulled component references
a CSS variable your installed tokens don't define — a silently unstyled property, no
error anywhere. Release notes flag these with a "requires `@vegastack/design ≥ x.y.z`"
note; when in doubt, `pnpm update @vegastack/design` before pulling components.

## Development practices

- **Reference consumer:** the `vegastack-design-starter` repo (ask the design-system
  owner) is the executable pattern reference — layout/provider wiring, table + form
  pages, smoke tests. Copy its patterns, not its code.
- **Customize via wrapper files, not in-place edits.** In-place edits show as `≈ drift`
  forever and keep the CI gate red — see
  [Working with components § Customizing](/docs/guides/components).
- **Own your states:** every list needs loading/empty/error states; the starter
  demonstrates each with the system's components.
- **Smoke-test what you copied.** You own these files now; a ~10-spec Playwright suite
  (dialog focus trap, toast fires, dark mode persists) is cheap and catches provider and
  portal regressions the type system can't.

## CI

```yaml
- run: pnpm typecheck
- run: pnpm build
- run: pnpm exec vegastack-design check-updates --fail-on-update
  env:
    CF_ACCESS_CLIENT_ID: ${{ secrets.CF_ACCESS_CLIENT_ID }}
    CF_ACCESS_CLIENT_SECRET: ${{ secrets.CF_ACCESS_CLIENT_SECRET }}
```

The drift gate turns upstream movement into a red build instead of a surprise. Full
pre-ship list: [Production checklist](/docs/guides/production-checklist).

## Deployment

There is **nothing design-system-specific at deploy or runtime**. The service token is
build-tooling credentials only — used by `shadcn add` and `check-updates`, never read by
app code, never in `NEXT_PUBLIC_*`, never in a bundle. Your deployed app serves copied
source and npm-installed CSS; it makes zero requests to `design.vegastack.com`.
