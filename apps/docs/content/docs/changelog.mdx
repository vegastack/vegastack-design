This page tracks what ships and how you receive it. The design system distributes as a **hybrid**:
two public npm packages (`@vegastack/design` — utilities, icons, Tailwind preset, CLI — and the
zero-dependency `@vegastack/design-tokens` it depends on) plus a **private shadcn registry** for components
(`@vegastack/ui`), which you copy in rather than install.

## Status: Released

<Callout type="info">
  Current versions: **`@vegastack/design` 0.1.1** · **`@vegastack/design-tokens` 0.1.0** ·
  `@vegastack/ui` 0.2.0 (private — drives registry item versions only). Releases flow through
  Changesets: merge a changeset to `main` → the automated Version PR → merge → CI publishes via
  npm OIDC trusted publishing (no tokens). Per-package histories live in each package's
  generated `CHANGELOG.md`.
</Callout>

## Release notes

What shipped in the initial releases (0.1.0 → 0.1.1), summarized from the package changelogs.

### `@vegastack/design-tokens` — color token system v2

- Unified on-fill text: every chromatic `*-foreground` resolves to one warm off-white in both
  themes (fixes `primary-foreground` reading brighter than the rest).
- Dark mode honors the spec — chromatic `fill` / `hover` / `active` / `foreground` are
  theme-independent; only `subtle`, `text`, and the chart scale vary by theme.
- Shipped as **real tokens** (no longer opacity-derived): `{family}-subtle`, `{family}-hover`,
  `{family}-active` for info/destructive/success/warning, plus `primary-hover`,
  `primary-active`, and `muted-foreground-faint`.
- The fail-closed `contrast-check` gate validates the flat `-subtle` tokens and the page-readable
  `-text` tokens on `background` / `card`; all pairs pass **WCAG 2.1 AA**.

### `@vegastack/design-tokens` · `@vegastack/design` — initial token + runtime layer

- `@vegastack/design-tokens`: DTCG → Style Dictionary OKLCH tokens, the Tailwind v4 `@theme inline` bridge
  (light/dark), `theme.css` + `base.css`, and a typed `tokens` model. Zero dependencies.
- `@vegastack/design`: the bundled Tailwind v4 preset (`preset.css` + `./preset` metadata) for
  external consumers, plus CSS re-exports of the token layer (`./theme.css`, `./base.css`,
  `./utilities.css`).
- `@vegastack/design/icons`: the sanctioned `Icon` / `BrandIcon` wrappers (lucide + thesvg).

### `@vegastack/design/icons` — animated + brand variants

- New `AnimatedIcon` wrapper for `lucide-animated` motion icons — size tokens (`xs/sm/md/lg`), a11y,
  and forwarding of the icon's `startAnimation()` / `stopAnimation()` handle. It imports no `motion`
  itself; `motion` is pulled only by the mirrored icon a consumer adds.
- `BrandIcon` now exposes every `thesvg` variant: `color | mono | light | dark | wordmark`.

### `@vegastack/design` — utilities + verifier

- `cn()` class-merge helper (clsx + tailwind-merge) used by every component.
- Ships the consumer-facing registry verifier as a bin with a fail-closed Sigstore-signature mode
  and a `--hash-only` local-dev mode.

### `@vegastack/design` — the `vegastack-design` CLI

- `vegastack-design check-updates` — compares your copied-in components (by their provenance header)
  against the live registry **by integrity hash**, so you know exactly what to re-pull. Reads the
  registry URL + headers from `components.json`; supports `--dir`, `--filter`, `--json`,
  `--fail-on-update` (CI drift gate), `--registry`, `--cwd`, `--no-color`.
- `vegastack-design verify` — the registry integrity preflight/post-write check.
- The bin is named `vegastack-design` (not `vegastack`) so it never collides with a platform CLI.

### `@vegastack/ui` — v2 token repoint + animated registry

- Components now use the shipped `-subtle` / `-hover` / `-active` tokens (e.g.
  `bg-destructive-subtle`, `hover:bg-primary-hover active:bg-primary-active`) instead of
  opacity-derived colors; placeholders use `muted-foreground-faint`. No hardcoded colors anywhere.
- The full `lucide-animated` icon set is mirrored into the private registry, so any can be added via
  `shadcn add @vegastack/<icon>` and consumed through `AnimatedIcon`.

<Callout type="info">
  `@vegastack/ui` is **private and unpublished**. Its version bump exists only to drive the registry
  item `meta.version` — you never `npm install` it. Components reach you through the copy-in flow
  below.
</Callout>

## How you receive updates

Two delivery paths, because the system is hybrid.

**Packages** (`@vegastack/design` + `@vegastack/design-tokens`) are normal npm dependencies — bump them
with your package manager when a new version publishes. They share a Changesets `linked` group:
releases that touch both give them the same version; otherwise versions may differ (e.g.
`design` 0.1.1 alongside `design-tokens` 0.1.0 — nothing changed in the tokens).

**Components are pulled, never pushed.** They are copied into your repo by the shadcn CLI, so an
upstream change does not silently rewrite your files. You decide when to re-pull, review the diff,
then overwrite.

```bash
# 1. See what changed upstream (compares your copy-in by integrity hash)
vegastack-design check-updates

# 2. Review the diff for a component before taking it
shadcn add @vegastack/button --diff

# 3. Pull the update in, overwriting your copy
shadcn add @vegastack/button --overwrite
```

### Status is by integrity hash, not version number

`check-updates` compares the **whole-canonical-item SHA-256** stamped in each component's provenance
header against the registry. That means a component reads **`up to date`** when the global
`@vegastack/ui` version bumped but *that component's content* didn't change — you only re-pull what
actually moved.

<Callout type="info">
  Every registry item carries a `meta.integrity` SHA-256 plus a `// @vegastack <name>@<ver>
  sha256-…` provenance header, and the consume step runs a fail-closed verify. If a hash doesn't
  match, the add is rejected rather than silently trusted.
</Callout>
