## Usage

Add the `TooltipProvider` once, at the root of your app — it owns the delay every tooltip shares.

```tsx
import {
  Tooltip,
  TooltipContent,
  TooltipTrigger,
} from "@/components/ui/tooltip";

<Tooltip>
  <TooltipTrigger>Hover</TooltipTrigger>
  <TooltipContent>
    <p>Add to library</p>
  </TooltipContent>
</Tooltip>;
```

## Anatomy

`Tooltip` is a compound component. Compose the parts inside the root:

<Anatomy name="tooltip" />

```text
TooltipProvider
└── Tooltip
    ├── TooltipTrigger
    └── TooltipContent
```

- `TooltipProvider` — the app-root wrapper that shares one delay across every tooltip, so moving
  between neighbouring triggers does not re-pay it. Its `delay` defaults to `0` here.
- `Tooltip` — the root that owns open state (`open`, `defaultOpen`, `onOpenChange`) and can be
  disabled outright (`data-slot="tooltip"`).
- `TooltipTrigger` — the element the popup describes (`data-slot="tooltip-trigger"`). Use `render`
  to make an existing control the trigger rather than nesting a second button inside it.
- `TooltipContent` — the portaled popup (`data-slot="tooltip-content"`) plus its positioner and
  arrow. It takes the positioner's `side`, `sideOffset`, `align` and `alignOffset` directly.

### Side

Use the `side` prop to change the position of the tooltip. It accepts the physical sides `top`,
`right`, `bottom` and `left` as well as the logical `inline-start` and `inline-end`, and flips away
from a viewport edge on its own.

A disabled native button fires no pointer events, so wrap it in a span and make the span the
trigger. This is the case the Button component's own `disabled` handling (FRM-4) exists to avoid —

## Accessibility

- **The popup is visual-only.** Base UI renders it with no `role="tooltip"` and wires no
  `aria-describedby` on the trigger — that is its documented design, not an oversight. The tooltip's
  text therefore reaches no screen reader on its own.
- **So the trigger must carry the name itself.** Give every trigger an `aria-label` that closely
  matches the popup's text, exactly as the fixtures on this page do. Without it, an icon-only
  trigger is unnamed for assistive technology even though the tooltip looks informative.
- It opens on hover **and** on keyboard focus, and <kbd>Escape</kbd> closes it — a tooltip that only
  answers the mouse is unreachable by keyboard.
- Nothing interactive belongs inside the popup: it disappears on blur, so a link or button in there
  can never be reached.
- The popup is portaled out of the trigger's DOM subtree; `TooltipContent` re-applies the nested
  theme scope on the positioner (OVL-13), so a tooltip raised inside a scoped surface keeps that
  surface's palette.
- Motion is limited to a fade and a small scale, and the global reduced-motion reset in `base.css`
  collapses both.

| Key               | Action                                      |
| ----------------- | ------------------------------------------- |
| <kbd>Tab</kbd>    | Focus the trigger, which opens the tooltip. |
| <kbd>Escape</kbd> | Close the open tooltip.                     |

## Deviations

Upstream's file plus `packages/ui/upstream/patches/tooltip.patch`. Every hunk:

- **OVL-13** — `TooltipContent` reads `useInternalThemeScope()` and attaches it to the Positioner
  inside the Portal. A portaled popup leaves its theme subtree, so a nested scope is lost by
  inheritance unless the host re-applies it; `tooling/verify-portal-theme-scope.mjs` inventories
  this host.
- **DOC-2** — `cn` is imported from `@vegastack/design`.
