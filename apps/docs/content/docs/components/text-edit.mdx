## Usage

```tsx
import { TextEdit } from "@/components/ui/text-edit";

const [html, setHtml] = useState("<p>Hello</p>");

<TextEdit
  value={html}
  onValueChange={setHtml}
  placeholder="Add a description…"
  aria-label="Body"
  aria-describedby="body-help"
/>;
```

`TextEdit` is **controlled** with `value` / `onValueChange` (HTML strings), or **uncontrolled** with
`defaultValue`. It is built on [Tiptap v3](https://tiptap.dev) `StarterKit`, which bundles undo/redo
history, the **bold / italic / strike / code** marks, **headings**, **bullet & ordered lists**,
**blockquote**, and markdown-ish input rules (type `**bold**`, `# Heading`, `- ` for a list,
`> ` for a quote, `` `code` ``).

```tsx
// Uncontrolled — seed initial content and read changes via onValueChange.
<TextEdit
  defaultValue="<p>Draft…</p>"
  onValueChange={(html) => save(html)}
  aria-label="Notes"
/>
```

### Light first paint

The editor is heavy (Tiptap and ProseMirror, ~180 KB gzipped), so `TextEdit` does not ship it in the
page's first bundle. It renders the saved value as plain read HTML first — the same
[`MarkdownView`](/docs/components/markdown-view) tree, in the editor's exact classes, on the server
too — and loads the editor on intent: a hover or touch starts the download, and a click, tap or
focus swaps the editor in place before the next paint. The caret lands where the click did, a click
on a task checkbox toggles it, and anything typed while the editor loads is kept. The swap is
invisible: the read view is `contenteditable` with the editor's role, label and focus cue, so it
looks, focuses and opens the keyboard exactly like the editor. `readOnly` and `disabled` never load
the editor at all.

`citation` is [`MarkdownView`](/docs/components/markdown-view)'s: in the read view a `[[n]]`
marker renders as a superscript citation, and pressing or focusing one is the citation's — it
never starts editing. In the editor the markers are plain `[[n]]` text.

Once the editor has loaded on a page, every `TextEdit` mounted afterwards swaps it in straight
away. To load it ahead of a first edit — a "New task" dialog about to open — call
`preloadTextEdit()`:

```tsx
import { preloadTextEdit } from "@/components/ui/text-edit";

<Button onPointerEnter={() => void preloadTextEdit()} onClick={openDialog}>
  New task
</Button>;
```

## Scope

`TextEdit` is the **presentational base editor** — a controlled HTML value, the StarterKit
formatting set, the slash and bubble menus, the placeholder, read-only mode, a `Cmd/Ctrl+Enter` `onSubmit`
affordance, and `minHeight`/`maxHeight` sizing. Heavier, app-coupled capabilities are intentionally
**out of this core** (each needs app infrastructure or ships as a separate composed extension),
mirroring the system's presentational / app-coupled rule:

| Capability                                                  | Why it's out of the base                                         | Where it lives                            |
| ----------------------------------------------------------- | ---------------------------------------------------------------- | ----------------------------------------- |
| Image upload / paste-to-upload                              | Needs app storage (R2/CDN)                                       | App resolves URLs (same split as `Image`) |
| @mentions                                                   | Needs the app's user/entity data                                 | App-supplied data source + query          |
| Emoji picker, syntax highlighting                           | Composed Tiptap extensions                                       | Future composed addons                    |
| Callouts                                                    | No clean CommonMark/GFM form to round-trip to                    | A quote, or a MarkdownView-only extension |
| Real-time collaboration (multi-cursor, awareness, Yjs CRDT) | Needs `@tiptap/extension-collaboration` + `yjs` + a sync backend | Separate `text-edit-collab` component     |

This base ships no `@tiptap/extension-collaboration` and no `yjs` dependency — it is a self-contained
single-user editor. For richer needs, compose the relevant extension on top or use the dedicated
follow-up component.

Prose styling is **not** this component's to own: the editor surface wears the shared `prose`
recipe from `@vegastack/design`, the same string `MarkdownView` puts on its root, so what a person
types here and what the app renders from markdown are one typography.

## Anatomy

`TextEdit` is the one component you use. It renders a light read view first and lazily loads
`TextEditEditor` (its own file, `text-edit-editor.tsx`, never imported directly) in its place:

<Anatomy name="text-edit" />

Inside, it composes these pieces:

```tsx
// data-slot="text-edit" data-variant — document: no border, no ring, no fill; boxed: a bordered field
<TextEdit>
  // Before the editor loads: data-slot="text-edit-read" — the saved value as MarkdownView, with the
  // editor's classes, role, label and focus cue, contenteditable while editable
  <MarkdownView />
  // Once loaded (text-edit-editor.tsx), in its place:
  // Tiptap contenteditable, role="textbox" aria-multiline data-focus-cue="caret" (boxed: "border")
  <EditorContent />
  // children — boxed only: inside the box, after the document (a composer's actions row)
  // In a <body> portal:
  // data-slot="text-edit-bubble-menu" — role="toolbar", over a selection
  //   (or text-edit-link / text-edit-image / text-edit-turn-into while a panel is open)
  <BubbleMenu />
  // data-slot="text-edit-slash-menu" — role="listbox", while typing after /
  <SlashMenu />
  // data-slot="text-edit-block-handle" — pointer-only drag handle beside the hovered block
  <BlockHandle />
  // over the hovered table: data-slot="text-edit-table-grip" (data-axis row | col | table) —
  // buttons that open a DropdownMenu and drag to reorder; data-slot="text-edit-table-add" — "+" bars
  <TableControls />
</TextEdit>
```

- **Root** (`data-slot="text-edit"`, `data-variant`) — in `document` mode transparent and borderless:
  it takes the surface it sits on. In `boxed` mode a bordered field whose border darkens subtly
  while the editor holds focus and turns destructive when invalid. Carries `data-editable` and
  `data-invalid` when it wraps an `aria-invalid` control. Clicking its blank space focuses the end
  of the document.
- **Bubble menu** (`data-slot="text-edit-bubble-menu"`, `role="toolbar"`) — a Turn into button,
  `Toggle` buttons for bold, italic, strikethrough, inline code and link, and Clear formatting;
  link swaps it for an inline URL input with Open and Remove (`data-slot="text-edit-link"`).
- **Block handle** (`data-slot="text-edit-block-handle"`) — a pointer drag handle; the keyboard has
  the same moves.
- **Table controls** — for the hovered table only: row, column and corner grips
  (`data-slot="text-edit-table-grip"`, `data-axis="row" | "col" | "table"`), each a labelled button
  that opens a `DropdownMenu` and drags to reorder (the corner moves the whole table, where every
  block's handle sits), and the "+" bars (`data-slot="text-edit-table-add"`) that add a row or a
  column at the end.
- **Slash menu** (`data-slot="text-edit-slash-menu"`, `role="listbox"`) — the block menu, in the
  Command item style with muted icons. Focus stays in the editor; the caret never moves.
- **Read view** (`data-slot="text-edit-read"`, `role="textbox"`) — the saved document as
  `MarkdownView` in the editor surface's classes, until the editor loads; see Light first paint.
- **Editor surface** (`role="textbox"`, `aria-multiline`) — the Tiptap/ProseMirror contenteditable.
  Prose is styled entirely with semantic tokens (headings, lists, code, blockquote), so it tracks the
  active theme with no `@tailwindcss/typography` dependency. It has no fill, border or ring in any
  state — in `document` mode the caret is the focus cue, in `boxed` mode the root's border — and
  nothing in it widens the page.

## Examples

### Slash menu, bubble menu and in-place editing

There is no toolbar. Type <kbd>/</kbd> for a filterable block menu (text, headings 1–4, lists, a
checklist, a quote, a code block, a table, an image, a divider, a link); `slashCommands` limits it.
Select text for a bubble menu with Turn into, bold, italic, strikethrough, inline code, link and
clear formatting. Every menu floats in a portal on `<body>` and flips to stay in view, so no
overflow container clips it. The editor has no view mode: leaving it calls `onCommit` when the text
changed, <kbd>Esc</kbd> reverts (`onRevert`), and `autosave` commits after an idle gap. Every
command, the shortcuts, the input rules and a view/edit parity example are on the
[Markdown guide](/docs/guides/markdown).

**Escape never erases saved text.** `escapeBehavior` decides what <kbd>Esc</kbd> does: `"revert"`
restores the document as focus found it, blurs and calls `onRevert` — a field you edit and then
confirm; `"blur"` keeps the text, commits it and blurs — a document that saves as you type. It
defaults to `"blur"` whenever `autosave` is set and to `"revert"` otherwise, so a page that
autosaves can never restore text older than what it already saved. A host that saves on its own
schedule (from `onValueChange`, say) calls `handleRef.current.markSaved()` after each acknowledged
save: the saved document becomes the baseline Escape reverts to and a commit compares against.

### Tables

Notion's simple table: a rounded outer border, a rule between every cell, and a header row on a
muted ground at medium weight — the same styles in the read view (`MarkdownView`) and the editor.
There is no toolbar; everything is on hover, for the hovered table only:

- **Row grip** (⠿ on the row's inner left edge) — click to select the row and open its menu:
  Insert above, Insert below, Move up, Move down, Duplicate, Clear contents, Delete row. Drag it to
  reorder rows.
- **Column grip** (on the column's inner top edge) — Insert left, Insert right, Move left, Move
  right, Duplicate, Clear contents, Delete column. Drag it to reorder columns.
- **Corner grip** (where every block's handle sits) — selects the whole table: Clear contents,
  Delete table; drag it to move the table. A fully selected table also deletes with
  <kbd>Backspace</kbd> or <kbd>Delete</kbd>.
- **"+" bars** below and beside the table add a row or a column at the end.
- **Column borders** drag to resize (`col-resize` cursor, a thin line on the border). Markdown has no
  column widths, so in `format="markdown"` a width lasts for the session; HTML keeps it.

<kbd>Tab</kbd> / <kbd>Shift</kbd> <kbd>Tab</kbd> move between cells and
<kbd>Tab</kbd> in the last cell adds a row; <kbd>Enter</kbd> stays in the cell;
`/table` inserts a 3×3 table with a header row. The header row always stays
first — GFM has no other place for it — and saves as GFM markdown that loads
back identically.

### Block handles

The ⋮⋮ handle beside the hovered block drags it (or a single list item) to a new place;

<kbd>Mod</kbd> <kbd>Shift</kbd> <kbd>↑</kbd> / <kbd>↓</kbd> does the same from
the keyboard. A table's handle is its corner grip (see Tables).
`dragHandles=false` turns the handle and all the table's hover controls off.

The handle is a narrow grip 3px before the text, so it fits inside the 16px padding of a Dialog,
Sheet, Popover or Card and never touches the container's edge; the text keeps its column, with no
indent while the handle is hidden. Where the padding is narrower — a `boxed` editor — the grip is
held just inside the frame.

### Document and boxed

`variant` picks the editor's chrome and focus cue. `document`, the default, is the Notion-style page
editor for a task description or a meeting summary: no border and no fill in any state, and the
caret is the focus cue — every other example on this page. `boxed` frames the editor in a bordered
field for a comment composer or a form field: the border darkens subtly (`border-ring/40`, easing in
over 150ms) while the editor holds focus, nothing fills, and a click anywhere in the box starts
editing. `children` render inside the box after the document — a composer's actions row.

### Markdown

`format="markdown"` makes `value`, `defaultValue`, `onValueChange` and `onSubmit` carry Markdown
instead of HTML, through Tiptap's own `@tiptap/markdown` extension: headings, bold, italic,
strikethrough, links, bullet, ordered and task lists, blockquotes, code, tables and images
round-trip unchanged — and so do mentions, callouts, toggles and file links. Loading a
document never fires `onValueChange`; only an edit does. Store what the editor emits and render it
elsewhere with [`MarkdownView`](/docs/components/markdown-view). The format is read once, when the
editor is created.

### Mentions

`mentions={{ kinds, search }}` turns on `@`: typed after a space or at the start of a line it opens
a menu grouped People · Pages · Files · Tasks (only the `kinds` given, at most five each). `search`
runs 150ms after the last keystroke with an `AbortSignal` that aborts when the query changes; the
menu shows "Searching…", "No matches" or "Couldn't search". <kbd>↑</kbd> <kbd>↓</kbd> move,

<kbd>Enter</kbd> or <kbd>Tab</kbd> pick, <kbd>Esc</kbd> closes. A pick becomes a
chip, stored as `[@Asha Rao](mention://user/u1)`, that <kbd>Backspace</kbd>
removes whole. `mentionHref(kind, id)` makes a chip open its target on
<kbd>Cmd/Ctrl</kbd>-click (and link it in the read view and `MarkdownView`); a
person never links, and an id starting with `restricted:` is a muted chip for a
target the reader may not open — the app keeps the real id after the colon so an
edit never loses the mention.

### Uploads

`onImageUpload(file, { signal })` takes images pasted, dropped, or picked with the image panel's
**Upload** (the slash menu's Image). The image shows dimmed under a spinner until the promise
resolves with `{ src }`, then lands in the document and commits — `onValueChange` and `onCommit`
both fire, even when focus has already left. A rejection removes the placeholder and calls
`onUploadError(file, error)`. `onFileUpload(file, { signal })` does the same for any other file
(dropped, pasted, or the slash menu's File) and inserts `[name](href)`; a link whose href starts
with `fileLinkPrefix` (default `/api/files/`) shows as a file chip. Without `onFileUpload`, other
files are ignored.

### Images

An image works like Notion's. Hover it (or tap it on touch) for a ⋯ menu at its top-right:
**Open** shows it in the `FileViewer`, paging through every image in the document (a double-click
does the same); **Download**; **Copy link** for an `http(s)` image; and **Remove image**, which

<kbd>Cmd/Ctrl</kbd>+<kbd>Z</kbd> undoes. Its corner and side handles resize it
with the aspect ratio kept — Tiptap's own `ResizableNodeView`, from 48px up to
the width left of the image — and while dragging, guides mark a quarter, a half,
three quarters and the full width, snapping within 8px. The width is part of the
document: `![alt|320](src)` in Markdown (the Obsidian convention, which
`MarkdownView` reads and other renderers show as a plain image) and
`width="320"` in HTML. `readOnly` documents and posted comments open their
images in the viewer on a click and have no handles or Remove; wrap any other
`MarkdownView` in `ImageViewerScope` for the same.

### Outline

`onOutlineChange` receives the headings (`#`–`####`) with stable ids — the heading's words,
hyphenated, `-1`, `-2`… for a repeat — after load and 150ms after each change; the same ids are on
the heading elements (and on `MarkdownView`'s with `headingIds`). `handleRef` gives an imperative
handle: `scrollToHeading(id)`, `flush()` (commit now, and wait for uploads in flight — before
creating a comment or navigating), `focus()`, `getAnchorForSelection()`, `pulseAnnotation(id)` and

### Comment highlights

`annotations` draws comment highlights — `{ id, anchor }`, where an anchor is offsets into the
document's text plus the quoted words and up to 80 characters of context (`TextAnchor`). They are
decorations, never written into the Markdown. Each anchor resolves on load (the stored offsets if
the words there still match, else the one place its context occurs, else the one place its quote
occurs, else orphaned), then rides along with edits: typing before a highlight keeps it on the same
words. `onCreateAnnotation(anchor)` adds **Comment** to the selection bubble — read-only too, never
in a code block. `onAnnotationsLayout` reports each highlight's `top` (px from the root; `null` when
orphaned) and its current `anchor`, for comments beside the text and for persisting moved anchors.
`activeAnnotationId` fills one highlight; `onAnnotationClick` and `onAnnotationHover` (after 250ms)
report the pointer. Setting `annotations` (or `onOutlineChange`) mounts the editor at once, and
`readOnly` then keeps it not editable with the highlights drawn.

#### Count pills and the keyboard

`annotationCounts` puts a count pill after each drawn highlight — the thread's `count` (absent
counts as 1) — so the text shows where comments are without hover or a margin. `"auto"` shows it
only on a coarse pointer or below the `lg` breakpoint, in CSS; `"always"` everywhere; `"never"` (the
default) renders none. The pill is a widget, `contenteditable="false"`: it is never in the document,
its Markdown or a copy, clicking it keeps the caret where it was, and it follows the active thread
(`data-active`). It has a 24px hit area and is named by `annotationCountLabel` (“3 comments”), the
visible number `aria-hidden`. Every highlight opens from the keyboard, through `onAnnotationClick`:
read-only, each is a tab stop named by `annotationLabel` (“3 comments on “25 A breaker””) that Enter
or Space opens; while editing, a focusable highlight would take the caret and Tab from the text, so
instead Alt+Enter with the caret in a highlight opens it. The pill is never a tab stop — the
highlight or the shortcut already is.

### Invalid

Pass `aria-invalid` to mark the editor invalid: it forwards to the contenteditable textbox and the
root carries `data-invalid`. A `document` editor draws no border, so the error text is the visible
cue; a `boxed` one also turns its border destructive (see [Boxed, invalid](#boxed-invalid)).
Connect the error text with `aria-describedby` so it is announced with the region. `aria-invalid`
also accepts `"grammar"` and `"spelling"`.

## Accessibility

- The editable surface is a `role="textbox"` with `aria-multiline="true"`. Give it an `aria-label`
  (or associate a visible label) so the region is announced.
- Use `aria-invalid` and `aria-describedby` to connect validation state and helper/error text to the
  contenteditable textbox.
- The slash menu is a `listbox` of `option`s with `aria-selected`; focus stays in the textbox and
  <kbd>↑</kbd> <kbd>↓</kbd>, <kbd>Enter</kbd> and <kbd>Esc</kbd> drive it.
- The bubble menu is a Base UI `Toolbar` labelled “Selection formatting”: one tab stop, arrow keys
  between its `Toggle`s, each with an `aria-label` and `aria-pressed`. With `onCreateAnnotation`
  it leads with a **Comment** button; read-only, the toolbar (“Selection actions”) holds only that.
- The mention menu is a `listbox` labelled “Mention” whose `group`s are named by their headings
  (People, Pages, Files, Tasks); focus stays in the textbox, as with the slash menu. A chip reads
  as its name.
- An upload placeholder is a `role="status"` named “Uploading” and the file’s name.
- A callout is a `role="note"` named by its tone; while editable its icon is a button, “Callout
  type: Note”, that changes the tone.
- Comment highlights are decorations with a dashed underline. With `onAnnotationClick`, a read-only
  highlight is a `role="button"` tab stop named by `annotationLabel` (“Comment on “…””): one per
  highlight, on its first text span, the rest of its text hidden from assistive tech because the
  name already quotes it; its focus is base.css's `accent` tint. While editing a highlight carries
  no role and is no tab stop, so the caret, Tab, typing and IME are untouched — Alt+Enter opens it
  instead. A count pill (`annotationCounts`) is a `role="button"` named by `annotationCountLabel`,
  out of the tab order.
- Editing keymaps come from Tiptap `StarterKit` plus a few of ours — see the table below. In
  `document` mode focus is shown by the caret itself: the surface has no ring, border or tint (it
  declares `data-focus-cue="caret"`). In `boxed` mode the box's border darkens subtly while the
  editor holds focus and nothing fills (`data-focus-cue="border"`); an invalid box keeps its
  destructive border. Either way forced-colours mode restores a system outline.
- The table grips are buttons labelled "Row options", "Column options" and "Table options"; each
  opens a Base UI `DropdownMenu` (arrow keys, <kbd>Enter</kbd>, <kbd>Esc</kbd>, focus returns to the
  editor). From the keyboard, <kbd>Shift</kbd> <kbd>F10</kbd> (or the context-menu key) in a table
  opens the menu for the selection: a selected column (<kbd>Shift</kbd> + arrows across cells), the
  whole table, else the caret's row. The "+" bars are labelled "Add row" and "Add column". The block
  handle is pointer-only and hidden from assistive tech, because <kbd>Mod</kbd> <kbd>Shift</kbd>
  <kbd>↑</kbd> / <kbd>↓</kbd> does the same from the keyboard.
- An invalid control (`aria-invalid`) sets `data-invalid` on the root for downstream styling; pair
  it with visible error text through `aria-describedby`.
- `readOnly` marks the surface read-only.
