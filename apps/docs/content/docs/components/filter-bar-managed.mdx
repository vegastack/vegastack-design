## Usage

```tsx
import {
  FilterBuilder,
  type FilterField,
  type FilterNode,
} from "@/components/ui/filter-bar-managed";

const VOCABULARY: FilterField<string>[] = [
  {
    key: "stage",
    label: "Stage",
    type: "text",
    operators: [{ value: "is", label: "is" }],
  },
];

const [tree, setTree] = useState<
  Extract<FilterNode<string>, { type: "group" }>
>({
  type: "group",
  op: "and",
  children: [],
});

<FilterBuilder vocabulary={VOCABULARY} value={tree} onValueChange={setTree} />;
```

This is the stateful sibling [`FilterBar`](/docs/components/filter-bar)'s docs
promised. **The grammar is host-injected**: the component owns the tree shape
(`FilterNode` — nested and/or groups and condition rows) and its editing
surface; your app supplies the `vocabulary` (which fields exist, which
operators each accepts, which editor type renders the value) and the `editors`
registry. The component never validates a field's semantics and never
serialises — the moment it did either, it would have adopted one app's AST.

## Scope

| Behaviour                 | Where it lives                                                            |
| ------------------------- | ------------------------------------------------------------------------- |
| The field grammar         | Host, via `vocabulary` — never baked in                                   |
| Value editors beyond text | Host, via `editors` (date pickers, actor pickers, …)                      |
| Serialisation / URL state | Host — the tree is plain data                                             |
| Running the filter        | Host — the output describes conditions; it never executes them            |
| AI-suggested filters      | Host — app-coupled per the [same split](/docs/components/data-list#scope) |

value with, exported so a host can register or reuse them.

### Operators and value shapes

Give each operator a `valueShape` — `none`, `scalar`, `list` or `range`. Switching between two
operators of the same shape keeps the value; switching to another shape clears it, so a single
value never survives into "is any of". `requiresValue: false` is shorthand for `none`. A missing
value shows "Value required" only after its control was left, or when the enclosing form is
submitted — never on a row that was just added.

### Condition rules (no groups)

For a rule editor — "Required when …", "Shown when …" — `allowGroups={false}` keeps the conditions
flat, `prefix` names the builder ("Required when" is the fieldset's name and leads the sentence),
and `labels` renames its own words (`addCondition`, `remove`, `matchAll`, `matchAny`, `empty`,
`valueRequired`, `field`, `operator`). `conditionError(condition, path)` returns a row's own
message: it shows under the row and is read as its value editor's description, beside the built-in
"Value required".

### Sentence summary

`summary="sentence"` makes the read-only summary one sentence instead of chips. The same text comes
from `describeFilter(tree, vocabulary, { prefix })` — for a list cell, a tooltip or an audit line.
Option values read by their labels, numbers carry the field's `unit`, ranges read as `10–20 W`,
`≥ 10 W` or `≤ 20 W` (`formatRange`), and nested groups read in parentheses.

### Value editors

Five editors ship with the item, for the `editors` registry or on their own: `TextValueEditor`,
`NumberValueEditor` (a `NumberField` with the field's `unit`), `NumberRangeEditor` (Minimum and
Maximum; either may be empty, and a minimum above the maximum is an error on the Minimum field),
`OptionValueEditor` and `OptionsValueEditor` (one or several of the field's `options` — one on a
`Select` up to seven options and a `SearchableSelect` above seven, several always on a
`SearchableSelect multiple`; both take `placeholder` and `searchLabel`). Without an
entry in `editors`, a `range` operator gets `NumberRangeEditor`, a `list` operator on a field with
`options` gets `OptionsValueEditor`, a field with `options` gets `OptionValueEditor`, and the rest get
`TextValueEditor`. `editors.range` and `editors.list` override the shape defaults.

For a long vocabulary, `fieldPicker="searchable"` makes each row's field picker a
`SearchableSelect`; `fieldPickerProps` reaches it, so `remote` with `useAsyncSearch` searches the
fields on the server (every field it offers must also be in `vocabulary`).

## Accessibility

- The tree is nested `<fieldset>`/`<legend>` structure — deliberately not
  `role="tree"`, where editing controls inside tree items are a known
  screen-reader trap. Every control stays an ordinary labelled form control.
- Removing a condition moves focus to the next condition in the same group, or
  to the group's add-condition button when it was the last — never back to the
  top of the page.
- A value-requiring condition without a value is flagged with visible text
  ("Value required") and `data-invalid`, never colour alone.
- A row's own error (`conditionError`) is read as the field picker's description, with
  `aria-invalid` — so it is announced even for an operator that takes no value.
- At the depth or condition cap the add affordances disable and the reason
  renders as visible text beside them.

| Key                                 | Action                                        |
| ----------------------------------- | --------------------------------------------- |
| <kbd>Tab</kbd>                      | Move through field, operator, value, remove.  |
| <kbd>Enter</kbd> / <kbd>Space</kbd> | Open the focused picker or activate a button. |
