## Usage

```tsx
import {
  Popover,
  PopoverContent,
  PopoverDescription,
  PopoverHeader,
  PopoverTitle,
  PopoverTrigger,
} from "@/components/ui/popover";

<Popover>
  <PopoverTrigger render={<Button variant="outline" />}>
    Open Popover
  </PopoverTrigger>
  <PopoverContent>
    <PopoverHeader>
      <PopoverTitle>Title</PopoverTitle>
      <PopoverDescription>Description text here.</PopoverDescription>
    </PopoverHeader>
  </PopoverContent>
</Popover>;
```

## Examples

### Composition

`PopoverContent` composes the portal, the positioner and the popup, so a popover is two parts at the
call site.

```text
Popover
├── PopoverTrigger
└── PopoverContent
    └── PopoverHeader
        ├── PopoverTitle
        └── PopoverDescription
```

### Basic

A header, a title and a description — the smallest popover that still names itself. `PopoverTitle`
labels the popup, so a screen reader announces the surface rather than its first sentence.

### Align

`align` on `PopoverContent` takes `start`, `center` (the default) and `end`, and decides where the
popup sits along the trigger's edge. `alignOffset`, `side` and `sideOffset` are forwarded to the same
positioner.

<ComponentPreview name="popoverAlign" file="components/preview/popover.tsx" />

### With Form

The popup is a focus-scoped surface, so form controls inside it are reachable and submit normally.
Give each `Input` an `id` that its `FieldLabel` points at — the popup portals out of the trigger's
subtree, and an implicit label would not survive the move.

<ComponentPreview
  name="popoverWithForm"

/>

### RTL

Wrap the subtree in `DirectionProvider direction="rtl"` so Base UI resolves the logical sides.
`side="inline-start"` and `side="inline-end"` swap with the reading direction; `left`, `right`, `top`
and `bottom` stay where they are named.

## Accessibility

- Renders Base UI's Popover: the trigger is a button with `aria-expanded` and `aria-controls`, the
  popup is a `role="dialog"` labelled by `PopoverTitle` and described by `PopoverDescription`, and
  <kbd>Esc</kbd> closes it and returns focus to the trigger.
- The popover is non-modal: the page behind it stays scrollable and interactive, and an outside press
  dismisses it.
- The popup portals out of the trigger's subtree, so `PopoverContent` re-applies the theme scope on
  the positioner inside the portal (OVL-13) — a dark or scoped surface survives the portal.
- Focus is the global 2px `:focus-visible` outline from `base.css`; there is no ring glow on the
  trigger or on anything inside the popup.
- Give the trigger an accessible name. When it is an icon button, that means an `aria-label`.

## Do / Don't

<DoDont
  do="Use a Popover for secondary content the user can dismiss and ignore — a filter, a short form, a detail panel anchored to its trigger."
  dont="Use a Popover for a decision the user must resolve before continuing, or for a list of commands — that is a Dialog and a DropdownMenu respectively."
/>

## Deviations

Upstream's file plus `packages/ui/upstream/patches/popover.patch`. Every hunk:

- **OVL-13** — `PopoverContent` reads `useInternalThemeScope()` and attaches it to the Positioner
  INSIDE the portal — the same host shape `select`, `combobox` and `tooltip` carry.
  `tooling/verify-portal-theme-scope.mjs` inventories this host.
- **BRD-1** — `PopoverContent` draws a real 1px `border border-border` instead of upstream's
  `ring-1 ring-foreground/10` box-shadow outline. A border survives forced colours and matches
  [Elevation](/docs/foundations/elevation); nothing else about the surface moves.
- **DOC-2** — `import { cn } from "cn"` becomes `@vegastack/design`; our npm layer owns `cn`.
- **DOC-1** — prettier reflow plus the `registry-stamp.mjs` provenance header the three-copy model
  needs; no decision of its own.
