# transitions.dev — third-party research (verified)

Date: 2026-07-15
Target: https://github.com/Jakubantalik/transitions.dev (live site: https://transitions.dev/)
Method: GitHub API (`gh api`) for repo metadata/license/commits/contributors, WebFetch of README + terms.html, and direct `contents` fetches of `package.json`, both `SKILL.md` files, both `_root.css` token files, and one full transition snippet (`06-modal.md`), read verbatim — not summarized from the landing page.

**Bottom line up front:** the owner's framing — "React component lib with about 12 transitions" — is wrong on both counts. It is **not a React/component library**; it's a **markdown-based AI-agent "skill"** (installed via `npx skills add`) whose payload is 21 (not 12) portable, framework-agnostic **vanilla CSS + vanilla JS snippets**, each internally tokenized against its *own* private motion scale that has nothing to do with ours. License status is genuinely mixed, not clean MIT. Recommend **inspiration-only** — cherry-pick 3–4 concepts, re-implement natively — do not npm-install it and do not verbatim-vendor its CSS.

---

## (a) What it actually is

- **Repo type:** a static site (`index.html` etc., 89.9% HTML / 9.2% JS) that doubles as the source for an **AI coding-agent skill**. The actual distributable artifact is `skills/transitions-dev/` — a `SKILL.md` (agent-facing instructions) plus 21 numbered reference `.md` files (`01-card-resize.md` … `21-accordion.md`), each containing a copy-paste CSS block + optional vanilla-JS orchestration snippet + a `prefers-reduced-motion` guard.
- **Not npm-installable as a UI dependency.** Root `package.json` is `"private": true`, has one script (`build/extract.mjs`, generates the skill markdown from the live site's own tuning), and is not published to npm. The only published/installable piece is `refine/` — `transitions-refine` (v0.3.34 as of fetch), a separate CLI (`npx transitions-refine live`) that injects a live timeline/tuning panel into a running app and talks to *your* coding agent to apply "refinements." That is developer tooling, not a runtime or component dependency.
- **Installation is literally `npx skills add Jakubantalik/transitions.dev`** — it drops the markdown skill files into your agent's skills directory so *your agent* can quote/paste snippets on request. This is conceptually adjacent to how *this* Claude Code session's `skills` list works (it is itself a Claude/Cursor/Codex "skill" package), not a UI library you'd add to `packages/ui`.
- **Companion skill `transitions-polish`** is the more interesting half: it doesn't ship new transitions, it *audits* a project's existing CSS/Tailwind/CSS-in-JS motion values and maps them onto a 5-dimension token scale (duration/easing/distance/scale/blur) via usage-based matching ("usage first, never nearest number"), and exposes `transitions review` / `transitions polish` commands. This is functionally a motion-linter+auto-fixer, and its *design pattern* (token-by-usage, open/close asymmetry rules, stagger-total budget) is worth studying even though its actual token values aren't ours.

## (c) Tech / compatibility

- **Zero dependencies for the snippets themselves.** No framer-motion, no GSAP, no `motion`. Pure CSS custom properties + CSS `transition`/`@keyframes` + vanilla imperative JS (`classList.add/remove`, `getComputedStyle().getPropertyValue()`, `setTimeout`, `void el.offsetWidth` reflow hack for replay).
- **Not React.** No JSX, no hooks, no components anywhere in the repo. The JS orchestration snippets are `document.querySelector` + manual class-toggling + manual `setTimeout`-based cleanup timers — this is the imperative pattern our system deliberately does NOT use. Every one of our 68 canonical components drives enter/exit via Base UI's declarative `data-starting-style`/`data-ending-style` attributes + a plain CSS `transition` (confirmed in `09-motion-animation.md`), which is strictly more idiomatic for a Base UI + React 19 codebase. Porting any of these snippets means **discarding the JS orchestration entirely** and re-deriving the visual effect as a Base UI-attribute-driven CSS transition (already straightforward for #5/#6/#7/#9/#16/#17/#21 since Base UI already emits the open/close state Base UI needs; harder for the JS-heavy ones like #2/#10/#11/#12/#19/#20 which do real per-element math or SVG path length reads that don't map onto a single CSS transition).
- **'use client' / SSR:** not applicable — there are no React Server/Client Component boundaries here at all; every snippet assumes direct DOM access at runtime (browser only). Anything using `pointermove`/`querySelector` would need `'use client'` if ported into a React component, same as any interactive leaf in our system already requires.
- **Tailwind v4:** no relation. It's plain CSS custom properties (`:root { --x: 300ms }`), not Tailwind utilities/`@theme`. It would need full re-authoring to become `duration-*`/`ease-*` Tailwind classes bridged from `@theme inline`, exactly the pattern our `packages/tokens` already uses.

- **`refine/package.json` declares `"license": "MIT"`** — but that's scoped to the `refine/` subpackage (the CLI tool / live-panel injector), per its own `files` list and `repository.directory: "refine"`.
- **`terms.html`** ("Terms & License - Transitions.dev Refine") confirms: *"Refine is released under the MIT License. Copyright © 2026 Jakub Antalik / Transitions.dev"* followed by full MIT text — but this page is explicitly scoped to **Refine** (the beta CLI/panel tool), covered by a "Beta software," "your agent token & credit usage," and "the agent changes your code" disclaimer block that only makes sense for the CLI, not the static CSS snippets.
- **The actual snippet content — `skills/transitions-dev/*.md`, the CSS itself — has no explicit license attached anywhere.** Root `package.json` is `"private": true` with no `license` field. The README's entire premise is "copy-ready, portable CSS snippet for each," and `SKILL.md`'s `## Output format` instructs an agent to *"Paste the chosen transition's CSS verbatim"* into the user's project — strongly implying the author intends the snippets to be copied (this is the whole product), but that is an **implied license, not a granted one**. This is a materially different legal posture than shadcn/ui (explicit MIT `LICENSE` at repo root covering the registry items) or our own vendored `lucide-animated` mirror (upstream-licensed, tracked).
- **Verdict: do not verbatim-vendor the CSS/markdown into `packages/ui` or the private registry.** There's a real, non-hypothetical gap between "clearly intended for copying" and "actually licensed for redistribution inside a commercial private registry with our own copyright/integrity-hash provenance headers stamped on it" (per `AGENTS.md`'s `// @vegastack <name>@<ver> sha256-…` header convention — stamping our own provenance on unlicensed third-party CSS is a real legal exposure, however small). If the owner wants to lean on this repo more heavily than "read it for ideas," get explicit written permission from Jakub Antalik first, or wait for the repo to add a root `LICENSE`.
- **Health:** genuinely active, not a toy — 2,055 stars, 78 forks, 145 commits, single author (`Jakubantalik`, 100% of commits — solo project, bus-factor 1), created 2026-04-21, pushed 2026-07-14 (1 day before this audit — actively shipping), 4 open issues, has Pages/CNAME (`transitions.dev` custom domain), a GitHub Actions workflow (`publish-refine.yml`), and a real npm-published sub-tool (`transitions-refine`). This is a serious, well-executed, currently-trending project (design/motion topic tags: `design`, `motion`, `motionskill`, `product`, `skill`, `ui-design`, `ux`, `ux-design`) — not a landing-page showcase — but it is young (3 months old at audit time) and single-maintained, which matters for "would we depend on it" even setting the license question aside.

## (e) Quality read

- **Durations/easings are hardcoded per-snippet, not tokenized against any shared scale by default** — every one of the 21 `_root.css` blocks ships literal `ms`/`px`/`cubic-bezier(...)` values (see table in §b). The companion `transitions-polish` skill's `_root.css` *does* define a shared 7-step duration scale (`--duration-stagger` 40ms → `--duration-very-slow` 500ms), a 6-value easing set, a 5-step distance scale, a 4-step scale-scale, and a 3-step blur scale — but that's a **second, optional, separately-installed skill**, not something the base transitions ship with, and it's a completely different vocabulary from ours (7 durations vs. our 3, includes two overshoot/bounce cubic-beziers we don't have and explicitly don't want per the owner's "no flashy effects" brief).
- **Would these be easy to re-express with OUR tokens?** Partially, and only for the subset that's already "standard/emphasized/exit"-shaped motion (modal, dropdown, panel, tabs, tooltip, accordion — categories #5/#6/#7/#16/#17/#21). Their own `--ease-smooth-out: cubic-bezier(0.22, 1, 0.36, 1)` is close in spirit to our `--motion-ease-standard: cubic-bezier(0.2, 0, 0, 1)` (fast-out-slow-in family) but not numerically identical — would need to swap to our curve, not import theirs. The bounce/spring items (#3 badge pop, #10 success check bob, #11 avatar return, #20 morph) use `cubic-bezier(0.34, 1.36, 0.64, 1)` and an extreme `cubic-bezier(0.34, 3.85, 0.64, 1)` overshoot — this is exactly the kind of curve our `09-motion-animation.md §f` already anticipated needing (`--motion-ease-spring`) for the owner's explicitly-requested "success bounce," but the *strength* of overshoot in transitions.dev's curves reads as considerably more "bouncy/flashy" than "very small overshoot... dense dev-tool aesthetic, not playful" that our own audit recommended. Any adoption needs its own tuned, subtler spring curve, not a copy of theirs.
- **`prefers-reduced-motion` handling: yes, real, and good.** Every one of the 21 snippets ships an explicit `@media (prefers-reduced-motion: reduce) { .t-x { transition: none !important; } }` block, and `SKILL.md`'s "Common mistakes" section calls out never stripping it. This is at least as disciplined as our own global reset in `packages/tokens/src/base.css`, though implemented per-snippet rather than globally — our global `transition-duration: 0.01ms !important` reset approach is actually more robust (catches everything automatically) than requiring every consumer to remember the per-snippet guard.
- **Accessibility beyond reduced-motion:** not really addressed — no ARIA guidance beyond "wire `aria-expanded`/`aria-selected`" as class-name hooks; nothing on focus management, live regions for the error-shake/success-check state announcements, or keyboard interaction. Base UI already handles all of that for us; transitions.dev's snippets assume you've built the accessible interaction layer yourself and are only providing the visual layer.

**Recommendation: (c), inspiration only.** Concretely:
1. Treat `06-modal.md`, `05-menu-dropdown.md`, `03-notification-badge.md`, `09-icon-swap.md`, `10-success-check.md`, `12-error-state-shake.md`, and `21-accordion.md` as **design references** — read them for "what does a well-executed version of this look like," then hand-author the CSS as Base UI `data-starting-style`/`data-ending-style` + `transition-*` using our existing `duration-fast/base/slow` and `ease-standard/emphasized/exit` tokens (adding a new `--motion-ease-spring` token, as `09-motion-animation.md §f` already proposed, tuned to a *much* smaller overshoot than transitions.dev's `cubic-bezier(0.34, 3.85, 0.64, 1)`).
2. The one piece of genuinely portable *technique* (not styling) worth lifting outright: the accordion's chevron-flip-instead-of-path-morph trick (`transform: scaleY(-1)` with a symmetric viewBox + `vector-effect: non-scaling-stroke`, avoiding Chromium-only `d:` path interpolation) — this is implementation know-how, not copyrightable CSS values, and directly informs whether our own `accordion.tsx`/`collapsible.tsx` chevron rotation (currently a simple `rotate-180`, per `09-motion-animation.md §a2`) has any Safari/Firefox gap worth checking.
3. Do **not** adopt: card-hover-tilt (#19, conflicts with "no flashy effects"), avatar-group-hover's extreme overshoot easing (#11), or any of the imperative JS orchestration patterns (`setTimeout`-based cleanup, manual reflow hacks) — Base UI's data-attributes already solve the "replay/interrupt" problem these JS snippets exist to work around.
4. Optionally message the maintainer (`Jakub Antalik`) if deeper reuse is ever wanted — the repo is active and single-maintained, so a license clarification request is plausible to get answered, given the terms.html precedent of already writing one MIT grant for `refine/`.

## (g) Overlap with the planned motion pack (`09-motion-animation.md`)

- **No numeric overlap.** Our system: 3 durations (150/200/300ms), 3 easings (standard `cubic-bezier(0.2,0,0,1)` / emphasized `cubic-bezier(0.3,0,0,1)` / exit `cubic-bezier(0.4,0,1,1)`). transitions.dev + transitions-polish: 7 durations (40/80/150/250/350/400/500ms) and 6 easings (including two bounce curves). None of their numeric values line up with ours except by coincidence (their `--duration-quick: 150ms` happens to equal our `--duration-fast`). **Do not import their scale** — it would reopen the "3 durations, 3 eases" locked decision implicitly, which the owner has not asked to reopen.
- **Direct conceptual overlap — same gaps, independently identified:** `09-motion-animation.md §d` already flagged, before this research started, exactly the same needs transitions.dev's catalog covers: icon-swap pop-in (`AutoSaveInput`, `CopyButton` — items #4/#9), badge appear (`NotificationBell` — item #3), success bounce (item #10, and our own proposed `--motion-ease-spring` in `§f` is the same idea as their `--ease-bounce`/`--ease-bounce-strong`), and error shake (implied by the owner's CLAUDE.md "error shake" preference, matches item #12 exactly though no current component implements it). This convergence is a good signal that our own gap analysis was directionally correct — transitions.dev is useful primarily as **validation + a mechanism reference**, not as a source of new requirements.
- **transitions-polish's *methodology* is worth studying independent of its token values:** the "usage first, never nearest number" matching rule and the "open faster/heavier than close, exceptions are symmetric-and-reversible motions (page slide, tabs, accordion, icon swap, text swap)" open/close-asymmetry rule are exactly the kind of per-category spec our own `09-motion-animation.md §f` "Per-category animation spec" table is building toward — e.g., our audit's suggestion to promote full-screen `Dialog`/`Sheet` to `duration-slow` while keeping menus at `duration-fast` mirrors transitions-polish's dropdown-open-250/close-150 vs. panel-open-400/close-350 asymmetry almost exactly, arrived at independently.
- **Page-level transitions (#8, page side-by-side) do not belong in `packages/ui` at all** — component-level motion (overlays, accordions, toasts, state feedback — everything else in the 21) is `packages/ui/registry/ui/*` territory; route/page transitions are `apps/docs`(or any consuming app's) App Router concern, implemented via React's View Transitions API (`<ViewTransition>`) per the `vercel-react-view-transitions` skill available in this environment, entirely separate from the component registry's token system. If the owner wants route transitions for the docs app itself, that's a distinct, later decision — not part of the component motion pack.
