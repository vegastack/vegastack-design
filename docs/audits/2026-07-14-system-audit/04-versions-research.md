## (b) shadcn ecosystem changes affecting our private registry

The repo's registry has a **fully homegrown integrity/signing layer** (`meta.integrity` SHA-256 + Sigstore-signed manifest + fail-closed consume preflight, per AGENTS.md) built *on top of* stock `registry.json`/`registry-item.json`. Confirmed against current docs:

1. **No native integrity/signing field exists upstream.** `registry-item.json`'s documented top-level fields are `$schema, name, title, description, type, author, dependencies, devDependencies, registryDependencies, files, tailwind, cssVars, css, envVars, font, docs, categories, meta` — `meta` is an open catch-all with no reserved sub-keys. [registry-item.json docs](https://ui.shadcn.com/docs/registry/registry-item-json) confirmed there is still no standard integrity/signing convention as of July 2026. **Our custom `meta.integrity` + Sigstore approach remains necessary** — nothing upstream replaces it. Low risk to keep as-is; worth re-checking on a 6-month cadence in case shadcn formalizes this (their May 2026 "Registry Include and Validate" release shows they're actively investing in registry tooling).

2. **New `include` field + `shadcn registry validate` command (May 2026).** `registry.json` can now `include` other `registry.json` files (each item's original relative path preserved on flatten) and `shadcn build` resolves them into one flattened output; `shadcn registry validate` checks schema compliance, duplicate item names, include-rule correctness, and local file paths — **without requiring a prior `shadcn build`**. [May 2026 changelog](https://ui.shadcn.com/docs/changelog/2026-05-registry-include) — this is a natural pre-flight check to slot into `registry:build`/CI ahead of the existing `verify-headers.mjs`/`verify-shadcn-consume.mjs` scripts, catching schema errors before the custom integrity-stamping step runs. Worth adopting as a cheap early-exit gate.

3. **Private registry auth pattern matches ours.** Bearer-token + custom-header auth via `components.json`'s `registries` block (`{"@name": {"url": ..., "headers": {"Authorization": "Bearer ${ENV_VAR}"}}}`), token stored in `.env.local`, consumed as `shadcn add @namespace/item`. [Authentication docs](https://ui.shadcn.com/docs/registry/authentication), [Namespaces docs](https://ui.shadcn.com/docs/registry/namespace) — this is the exact shape AGENTS.md/docs/RELEASING.md already describe for service-token-only `/r/*` auth; no drift to correct.

4. **CLI v4 (March 2026) additions relevant to us:** `shadcn/skills` (bundles agent-facing context about a registry's components/patterns — directly relevant since this repo explicitly targets "humans and AI coding agents"), `--dry-run`/`--diff`/`--view` inspection flags (useful for the `check-updates` → `shadcn add --diff` → `--overwrite` downstream-consume runbook already documented), `registry:base`/`registry:font` item types (could let the registry distribute the whole design-system config — colors/theme/icons/fonts/radius — as one consumable "preset" item, which is adjacent to but not currently how `@vegastack/tokens`/`tailwind-preset` are distributed). [CLI v4 changelog](https://ui.shadcn.com/docs/changelog/2026-03-cli-v4)

5. **Base UI is now the CLI default (July 2026), not just supported.** `shadcn init` defaults to Base UI unless `-b radix` is passed. Since this repo already pins `--base base` explicitly (per AGENTS.md locked decisions), **this changes nothing operationally** — it just means the repo's choice is now the path of least resistance for anyone re-running `init`, rather than a deliberate opt-in. No migration needed; Radix remains fully supported if ever needed. An AI-assisted Radix→Base UI migration skill now exists (component-by-component, one commit each, report in `.migration/`) in case any lingering Radix code is ever found. [Base UI as the Default](https://ui.shadcn.com/docs/changelog/2026-07-base-ui-default)

6. **GitHub-native registries (June 2026)**: any repo with a root `registry.json` can now be installed from directly (`shadcn add <user>/<repo>/<item>`), no hosting infrastructure required. Not directly actionable for a *private* registry (this repo intentionally hosts via Cloudflare with service-token auth, not a public GitHub-registry pattern) but worth knowing this exists as a lighter-weight pattern for any future fully-public/OSS registry spinoff.

[Tailwind CSS v4.1 blog](https://tailwindcss.com/blog/tailwindcss-v4-1) (for the earlier 4.1 baseline), 4.3-specific scrollbar/shadow-color items found via search summary — recommend confirming exact 4.3.2 changelog against `github.com/tailwindlabs/tailwindcss/blob/main/CHANGELOG.md` before relying on specifics.

## Summary (10 lines)

1. **TypeScript is a full major behind (6.0.3 → 7.0.2, the Go-native "Corsa" compiler)** — do not jump yet, the stable programmatic API (needed by `typescript-eslint`/`ts-morph`) doesn't land until 7.1; official path is 5→6→7, not direct.
2. **`react-day-picker` is a full major behind (9.14.0 → 10.0.1)** — removed deprecated props/exports and **changed grid markup**; audit `date-picker.tsx` for both before bumping.
3. **ESLint is a full major behind (9.39.4 → 10.7.0)** — low risk given the repo is already flat-config on modern Node, but config lookup now starts per-file-directory not CWD; re-verify monorepo lint after bumping.
4. **shadcn CLI is 6 minors behind (4.7.0 → 4.13.0)** — no breaking changes for our setup; brings `include`-based registry composition + `shadcn registry validate`, worth wiring into `registry:build` as a pre-flight gate.
5. **Nothing upstream in shadcn replaces our custom `meta.integrity` + Sigstore signing** — confirmed `registry-item.json` still has no reserved integrity/signing field as of July 2026; the homegrown layer stays necessary.
6. **`@shadcn/react` (the sanctioned non-Base-UI exception) is a minor behind (0.1.0 → 0.2.1)** and shadcn shipped a wider chat-component family (`Bubble`/`Attachment`/`Marker`) on the same primitive in June 2026 — if any of those get adopted later, the AGENTS.md exception language needs updating from "message-scroller only" to the family.
7. **Base UI (`@base-ui/react` 1.6.0) is already at latest** and, as of July 2026, is now shadcn's own CLI default (previously just supported) — zero action needed since this repo already pins `--base base` explicitly.
8. **`lucide-react` has an internal version-pin mismatch** (`^1.21.0` in `apps/docs` vs `^1.20.0` in `packages/ui`/`packages/icons`) — no functional bug today since both ranges resolve to the same latest, but the pins disagree and should be aligned; upstream itself has no new breaking changes since the v1.0 icon-rename cutover.
9. **WCAG 2.1/2.2 AA + axe remains the correct, legally-operative accessibility target for 2026** — WCAG 3.0 won't be a Recommendation until ~2029 and APCA was formally dropped from its normative draft in 2023; do not treat APCA as a contrast-gate replacement.
10. **DTCG reached stable spec version 2025.10 (format + new Resolver module) and Style Dictionary 5.x already targets it** — tokens pipeline is spec-aligned; the one open question (not resolved in this pass) is whether the repo's light/dark theming uses the new Resolver-module multi-file/modifier convention, worth a follow-up read of `packages/tokens/build-tokens.mjs`.
