design.md — three approaches, and how we build ours

A side-by-side of Vercel (Geist), Resend, and our Aster reference, pulled from their live design.md files — to answer one question: how should VegaStack publish its own design system as an agent-readable contract? The headline finding: the three aren't variations on one format — they're two different genres, and the right move is to combine them.

1 · The core insight — two genres, not three styles

Genre A — the self-contained spec

Vercel (17.8 KB) and our Aster reference (70 KB). One file: DTCG-style frontmatter with the full token set, then prose (Colors, Typography, Layout, Elevation, Motion, Shapes, Components, Voice, Do/Don't). An agent can read it cold and build correctly. It is the design system, serialized.

Genre B — the pointer

Resend (1.1 KB). Not a spec at all — a thin redirect: npx skills add resend/design-skills plus links to its SKILL.md files. The canonical, versioned content lives in an Agent Skill repo, not the markdown. The .md is a discovery surface.

Why this matters for us: we already have both halves — a DTCG token pipeline (can emit a Vercel-style spec) and a skills/ directory (can be the Resend-style versioned source). We don't have to choose. We generate the spec from the tokens and distribute it through the skill.

3 · The idea worth stealing — Vercel's intent-encoded color scale

Vercel's most systematic move: every non-background scale runs 10 steps where the step number encodes intent, not just lightness. Same scale, predictable roles. Rendered from the real Geist tokens:

Gray (the chrome ramp)

Blue (accent — links, focus, info; blue-700 #006bff is the brand)

⚠ The non-monotonic step you caught — it's real, and it's a lesson. In Vercel's actual data, gray-400 #eaeaea (lum 0.823) is lighter than gray-300 #e6e6e6 (lum 0.791), and blue-900 is lighter than blue-800 — flagged with * below. Not a rendering bug: Vercel's scale encodes intent, not lightness — 300 = "active background", 400 = "default border", tuned independently for their roles, so lightness isn't monotonic at that boundary. Lesson for our ramp: if we ship a documented primitive ramp, choose deliberately — strict-monotonic lightness (cleaner, predictable; my recommendation) vs Vercel-style intent-encoding (role-precise but visually non-monotonic). I'd keep intent in our semantic layer and make the raw ramp strictly monotonic.
My judgment — adopt the clarity, not the API.

Vercel's steps are its component API (button = gray-1000 fill, gray-alpha-400 border). Ours is semantic (bg-primary, border-border) and 64 components depend on it — switching the API is out of scope. But the intent mapping is a brilliant documentation model. So:

  • Keep semantic tokens as the component contract (locked).
  • Add a documented primitive ramp with intent labels (100 bg → 400 border → 700 fill → 1000 text) so consumers get Vercel's mental model.
  • Steal the gray-alpha-* idea outright — it's exactly our hairline-border decision (translucent, composites over anything). We already chose this.
  • Steal the P3 wide-gamut oklch() variants — trivial for us since we're already OKLCH-native; Vercel ships hex+P3, we'd ship OKLCH (which IS P3-capable) with an sRGB-hex fallback noted.

5 · Recommended model for VegaStack

Synthesis: one source of truth → two published artifacts.

  1. Source of truth = @vegastack/tokens (DTCG). Already exists. Everything derives from here — nothing is hand-maintained twice.
  2. Artifact 1 — design.md (Vercel/Aster genre): a generated self-contained spec. A small script reads the DTCG tokens + a prose template and emits frontmatter (colors, type, spacing, radius, shadows, components) + the narrative sections. Generated, so it can never drift from the real tokens — an edge over Vercel's apparently hand-maintained file.
  3. Artifact 2 — the Skill (Resend genre): skills/design-system/ with the references/ depth layer (the part we found missing earlier: tokens.md, heuristics/, patterns/, components catalog). Distributed via the registry / npx. The .md can carry a Resend-style pointer to it.
  4. Consistency gate: CI re-generates design.md and fails if it differs from the committed copy (same fail-closed discipline as our contrast + registry-hash gates).
Reconnects the deferred work: the Skill references/ we postponed and this design.md share one source. When we pick the skills layer back up, the generator feeds both — so it's not duplicate effort.

6 · Proposed outline for vegastack/design.md

Concrete skeleton — Vercel's structure, Aster's rigor, our OKLCH/semantic reality. The frontmatter is machine-generated from tokens; the prose is templated.

7 · Build path (after you review)

  1. Phase 1 of the token plan lands first — the spec must describe the final tokens, not today's.
  2. Write tooling/gen-design-md.mjs: reads packages/tokens/dist/tokens.json + a prose template → emits design.md (+ design.dark.md like Vercel, or one file with both themes).
  3. Add a CI check: regenerate & git diff --exit-code (drift = fail).
  4. Author the prose sections once (Overview, Voice, Do/Don't, Accessibility) — the only hand-written part.
  5. Publish: the static spec at a stable path; the richer guidance via the Skill. (Publish step is operator-triggered, per house rule.)

8 · Bottom line

Don't copy Vercel or Resend — combine them, and beat both on freshness by generating from tokens. Vercel gives us the format and completeness; Resend gives us versioned distribution; Aster gives us the rigor and the aesthetic. Our differentiator is the OKLCH-native, DTCG single-source pipeline that lets the design.md and the Skill stay provably in sync with the actual shipped tokens — something a hand-maintained file can't guarantee.
