## Decisions and why (several came from real bugs found via vitest-browser, not guesses)

1. **`ComboboxInput` is styled standalone** (full border, `h-(--size-sm|md|lg)`, matches `Input`'s
   `fieldClasses` almost verbatim) — usable bare. **`ComboboxInputGroup`** is the bordered wrapper for
   input + adornments (trigger/clear/chips); it strips the _nested_ input's own border/background via
   a `[&_[data-slot=combobox-input]]:border-none …` descendant selector — the exact technique
   `field.tsx`'s `CONTROL_SLOTS` already uses in this codebase to flatten a nested control into its
   host's chrome. This avoids a double border without needing a "grouped" prop/context on `ComboboxInput`
   itself. `ComboboxInputGroup` sets `min-height` (not `height`) on the size scale, since it must grow
   when `ComboboxChips` wraps to multiple lines.

2. **`ComboboxTrigger` defaults to a compact icon-only square** (`size-(--size-sm|md|lg)`, ghost-button
   styling lifted from `button.tsx`'s `ghost`/`icon-*` variants), not a full `SelectTrigger`-style
   button — because the primary Combobox composition is "attached to an input", per the task brief. A
   `Select`-style button trigger (no visible input, `ComboboxValue` inside) is still fully supported by
   overriding `className` (`twMerge` resolves the conflicting size/border utilities) — documented with
   an example in both the component JSDoc and the MDX. Default child is `ChevronsUpDown` — per the
   house policy this is THE combobox chevron, and unlike `Select`'s `ChevronDown` it does **not**
   rotate on open (it's already bidirectional/open-or-closed), so there's no
   `group-data-[popup-open]:rotate-180` needed.

3. **`Combobox` (root) does NOT force `modal={true}`** — it passes `modal` straight through to Base UI,
   whose own default is `false`. This reverses my first instinct (mirroring `Select`'s
   `modal={true}` default) after a real, reproduced bug: with `modal` on, Base UI renders an inert
   backdrop with a `clip-path` hole carved out for the anchor's bounding box _at the time the popup
   opened_. In `multiple` mode, adding a chip grows `ComboboxInputGroup` (chips wrap), but the clip-path
   hole doesn't grow with it — so `ComboboxChipRemove` buttons outside the stale clipped region become
   genuinely unclickable (Playwright locator hung indefinitely; confirmed by inspecting the backdrop's
   `style` attribute and reproducing with/without `modal`). `modal` is still available as an opt-in for
   single-select, button-trigger-style usage. This is called out in both the component's JSDoc comment
   and an MDX "Modal usage" section, since it's a real footgun a consumer could hit by "obviously"
   copying `Select`'s modal-by-default convention.

4. **`ComboboxContent` does NOT auto-wrap `children` in `ComboboxList`** (unlike `SelectContent`
   auto-wrapping in `SelectList`, which the task brief's phrasing suggested mirroring). Reason, also a
   reproduced bug: `role="listbox"` only permits `role="option"`/group children per ARIA. `ComboboxEmpty`
   renders `role="status"`; if `ComboboxContent` force-wraps _everything_ passed to it (including
   `ComboboxEmpty`) inside one auto-rendered `List`, axe's `aria-required-children` rule fails — caught
   by the component's own "no a11y violations — open" test, not by inspection. Fix: `ComboboxContent`
   renders `Portal → Positioner → Popup → {children}` only; the consumer composes `ComboboxList`
   themselves as a **sibling** of `ComboboxEmpty`/`ComboboxStatus`. `ComboboxList` is still exported
   (mirrors `SelectList`'s existence) for direct composition — it's just no longer implicit.

5. **Filtering only works with the function-child (`Combobox.Collection`-wrapping) pattern on
   `ComboboxList`, not static `ComboboxItem` children** — this is a real Base UI behavior (not my
   design), reproduced via test: with `items` passed to the root but `ComboboxItem`s rendered
   statically (à la `SelectItem`), typing does not narrow the list, and `ComboboxEmpty` disagrees with
   what's actually rendered (it reports "no matches" while all static items stay visible) because
   `Empty`'s visibility is driven by the _derived filtered items count_, independent of the static DOM.
   Documented prominently (component JSDoc, MDX "Usage" section, and a code comment on the `Fixture` in
   the test file) since it's the single easiest way to misuse this component.

6. **Grouped rendering needs `useComboboxFilteredItems()`, not the original static groups array** —
   another reproduced-not-guessed finding. `ComboboxGroup`'s own `items` prop is read **verbatim** by
   its nested `ComboboxCollection` (confirmed by reading Base UI's `ComboboxGroup.mjs`/
   `ComboboxCollection.mjs` source: `ComboboxCollection` prefers `groupContext.items` over the root's
   `filteredItems` whenever it's inside a `ComboboxGroup` that received an `items` prop). So mapping the
   _original_ groups array into `<ComboboxGroup items={group.items}>` never filters. Fix: added
   `useComboboxFilteredItems` as a thin, documented re-export of Base UI's own public
   `Combobox.useFilteredItems` hook; the docs/preview/test grouped examples all call it and map over
   its _result_ instead. Verified end-to-end: typing narrows both which groups show items and which
   items show within a group.

7. **The `ComboboxChip`'s children are NOT wrapped in an inner `<span>`** — an earlier draft wrapped
   `{children}` (label text + the composed `ComboboxChipRemove`) in a single `<span className="truncate">`,
   which nested the remove _button_ inside that span too. Not an a11y violation per se, but it broke
   real interaction in a browser test (the remove button became unreachable via its accessible role in
   one repro, though the direct cause turned out to be the `modal` issue in #3 — the span-wrapping was
   an independent smell fixed at the same time since it serves no purpose once the remove control is a
   sibling, not nested content).

8. **`ComboboxValue`'s wrapping `<span data-slot="combobox-value">` gets marked `aria-hidden="true"` by
   Base UI while the popup is open** (confirmed empirically, not documented anywhere I found in the
   .d.ts/JSDoc) — verified this is `multiple`-mode-and-popup-open specific and clears the instant the
   popup closes. Read as intentional: while the listbox is being browsed via `aria-activedescendant`, a
   screen reader shouldn't also be pulled into the chip-row summary. Consequence: an accessibility-tree
   query (Playwright's `getByRole`, or a real screen reader) cannot reach a `ComboboxChipRemove` while
   the popup is open — a sighted mouse click still works (aria-hidden doesn't block pointer events, only
   AT traversal). Documented in the MDX's "Multiple selection" section and as an inline comment in the
   test that removes a chip (it closes the popup with `Escape` first, matching how an AT user would
   actually have to do it).
