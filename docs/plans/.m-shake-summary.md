# Phase M — error-shake replay system (summary)

Scope: `use-animation-replay.ts` (new hook) + auto-shake wiring in `input.tsx`, `otp-input.tsx`,
`checkbox.tsx`, `radio-group.tsx`, `field.tsx`.

## Mechanism chosen: class-toggle, not key-remount

Both mechanisms from the brief were evaluated:

- **Key-remount** (`key={replayKey}`) — simple, but remounting an element blurs it and resets
  native input state if it (or a descendant) was focused. A form control shaking because it just
  became invalid is exactly the element most likely to be focused at that moment. Wrapping an
  *ancestor* instead doesn't help either: changing a parent's `key` unmounts its whole subtree,
  including the focused input inside it.
- **Class-toggle + `animationend` cleanup** — the element's identity never changes, so focus,
  value, and selection survive. Restarting mid-animation needs an explicit "off, then on again
  next frame" cycle (a CSS `animation` only replays when it newly starts applying).

Verified by test (`use-animation-replay.test.tsx`, "shaking a focused input preserves focus,
value, and caret/selection"): focus an `<input>`, set value + selection, trigger the observed
element's invalid transition with **no click on any other element** (a `<button>` click would
have stolen focus itself in Chromium — an early version of this test was a false negative for
exactly that reason before the harness was fixed to trigger the transition via a `setTimeout`
instead of a click), then assert `document.activeElement`, `.value`, `.selectionStart/End` are
all unchanged after the shake plays. Class-toggle passes; key-remount was never shipped, so
class-toggle is the **one** mechanism the hook uses everywhere (form controls and — via
`useAnimationReplay` directly — non-form elements alike), rather than branching by element type.

## Two-layer API (`use-animation-replay.ts`)

1. **`useAnimationReplay(animationClassName)`** — low-level primitive. Returns
   `{ isActive, className, onAnimationEnd, replay }`. `replay()` always does an "off → next
   `requestAnimationFrame` → on" cycle (not just when already active), which is what makes a
   restart mid-animation clean rather than a no-op: React batching means a synchronous off+on in
   the same tick would collapse into one commit the browser never sees as two states, so the
   re-application is deferred one frame. `onAnimationEnd` checks
   `event.target === event.currentTarget` so a bubbled animation from a *descendant* (e.g. an
   icon with its own independent animation) can't clear the parent's state early — tested.
   General-purpose: any `motion-*` utility can be replayed this way, not just `motion-shake`.

2. **`useShakeOnInvalid({ shakeSignal? })`** — the form-control-specific convenience, built on
   #1, hardcoded to `'motion-shake'`. Returns `{ invalidRef, className, onAnimationEnd, isShaking }`.

   **Key finding that shaped this hook's design**: `aria-invalid`/`data-invalid` cannot be read
   as a React *prop* on these wrapper components in the common, Field-driven case. Verified by
   reading `@base-ui/react`'s source directly:
   - `@base-ui/react/input`'s `Input` **is** `Field.Control` (`Input.js`: `return Field.Control(props)`).
   - Checkbox's `CheckboxRoot`, Radio's `RadioRoot`, and `OTPField.Root` all import and call
     `useFieldRootContext`/register with Field internally.

   All four self-register with Base UI's Field context and get `aria-invalid`/`data-invalid`
   written **directly onto the real DOM node** by Base UI — it never round-trips back through our
   wrapper component's own React props. So `<Field error="…"><Input /></Field>` (the documented,
   common composition — confirmed working via a scratch test before committing to this design)
   never gives our `Input` function an `aria-invalid` *prop* to read; the attribute only exists on
   the rendered element. `useShakeOnInvalid` therefore attaches a `MutationObserver` to the DOM
   node directly (via `invalidRef`, a ref callback) watching exactly those two attributes — this
   works uniformly whether the invalid state came from Field context or a manually-passed
   `aria-invalid` prop (verified both paths with tests).

   Does **not** shake a control that's already invalid at mount (only a live false→true
   transition fires it — pre-rendered server-validated errors shouldn't shake on first paint).
   `shakeSignal` (any comparable value, e.g. a submit-attempt counter) re-triggers the shake for
   repeated failures against an *already*-invalid control, since the transition only fires once.

3. **`mergeRefs(...refs)`** — small composition helper so a component's own forwarded `ref` and
   `useShakeOnInvalid`'s `invalidRef` can both land on the same DOM node.

## Per-component wiring

| Component | Shake target | Trigger | Notes |
|---|---|---|---|
| `Checkbox` | `BaseCheckbox.Root` (the visible box) | own `aria-invalid`/`data-invalid` | new `shakeSignal?: unknown` prop |
| `RadioGroupItem` | `Radio.Root` (each item) | own `aria-invalid`/`data-invalid` | item-level, matching existing invalid-styling scope (not group-level); `shakeSignal?` prop |
| `Input` | standalone: the `<input>` itself. Addon mode (`prefix`/`suffix`): the `input-group` wrapper `<div>`, since that's the element with the visible border — shaking the bare `<input>` inside it wouldn't move anything the eye reads as "the field" | own `aria-invalid`/`data-invalid` | **Now `'use client'`** — the `MutationObserver` requires refs/state, so this component is no longer server-safe/hook-free (documented in its own JSDoc). `shakeSignal?` prop. Tested with a realistic "typing in a focused field triggers live validation" scenario, not just a button click. |
| `OTPInput` | `OTPField.Root` (the whole slot row, `data-slot="otp-input"`) | own `aria-invalid`/`data-invalid` (Base UI only sets `data-invalid` when wrapped in `Field.Root`; a manually-passed `aria-invalid` also works since it's read from the DOM either way) | Shakes the row once, not each slot independently; `shakeSignal?` prop |
| `Field` | **no shake of its own** — see below | — | `FieldError` gets `motion-enter-up` (mount-triggered slide+fade, already-sanctioned utility) |

### Why `Field` doesn't also shake (avoiding a double-shake)

Investigated both options from the brief ("FieldError's appearance" vs. "the control row").
Since all four leaf controls above already self-register with Field context and therefore already
receive `aria-invalid`/`data-invalid` — and therefore already shake themselves — having `Field`
*also* drive a shake on a wrapper around its `children` would double up for the common
`<Field error="…"><Input /></Field>` composition: the row would shake **and** the control inside
it would shake again, stacking into an amplified, un-subtle motion (violates "keep it ONE shake,
subtle"). Verified this composition actually produces a working self-shake via a scratch
integration test before deciding, then made it permanent
(`field.test.tsx`: "a bare Input nested in Field auto-shakes once when Field becomes invalid").

So `Field`'s only change is giving `FieldError` the `motion-enter-up` class. Base UI only renders
`Field.Error` while invalid (mounts fresh on every new error), so the slide-in replays for free on
every new error with no JS needed. Combined with the control's own independent shake, this
produces the "message sliding in + control shaking" combo from the brief — via two independent,
already-correct mechanisms, rather than one delegating motion-triggering to the other.

If a future control that does *not* self-register with Field is composed inside `Field` (outside
this phase's scope: Select, Textarea, etc.), it will only get the message slide-in, not a shake —
an acceptable, documented gap.

## `registry.json` snippet (not applied — `registry.json` is out of scope for this phase)

Modeled on existing `registry:ui` entries; used `registry:hook` per the upstream shadcn registry
schema's dedicated type for hook-only items (no other item in this registry.json uses it yet, so
there's no local precedent to match against — this is the standard shadcn schema type for exactly
this case).

```json
{
  "name": "use-animation-replay",
  "type": "registry:hook",
  "title": "useAnimationReplay / useShakeOnInvalid",
  "description": "Replay a mount-style CSS animation (e.g. motion-shake) on demand via class-toggle, without remounting the element — preserves focus/caret/selection on form controls. Includes useShakeOnInvalid, the auto-shake-on-invalid-transition convenience built on it.",
  "categories": ["hook", "motion"],
  "dependencies": [],
  "registryDependencies": [],
  "files": [
    {
      "path": "packages/ui/registry/ui/use-animation-replay.ts",
      "type": "registry:hook",
      "target": "@ui/use-animation-replay.ts"
    }
  ],
  "meta": {
    "whenToUse": "Replaying a motion-* utility on a user action (error shake, retry pop, etc.), especially on an element that might be focused (form controls) where a key-remount would steal focus.",
    "whenNotToUse": "One-shot mount animations that never need to replay — just apply the motion-* class directly.",
    "version": "0.1.0"
  }
}
```

`checkbox`, `radio-group`, `input`, `otp-input`, and `field`'s existing `registry.json` entries
each need `use-animation-replay` added to their `registryDependencies` array (they now import from
it). Not applied here — `registry.json` is forbidden for this phase.

## Test evidence

Scoped run (`packages/ui`, real Chromium via `@vitest/browser-playwright` — not jsdom, so real CSS
animations and `animationend` events are exercised via injected `<style>` mirrors, same technique
as `checkbox.test.tsx`'s touch-target suite and `animated-number.test.tsx`'s fast-tween mirror):

```
npx tsc --noEmit
  → clean

npx vitest run registry/ui/use-animation-replay.test.tsx registry/ui/input.test.tsx \
  registry/ui/otp-input.test.tsx registry/ui/checkbox.test.tsx \
  registry/ui/radio-group.test.tsx registry/ui/field.test.tsx
  → 6 files, 101 tests passed (0 failed)

node ../../tooling/design-lint.mjs registry
  → clean
```

`use-animation-replay.test.tsx` (13 tests) covers: rest state has no class; `replay()` applies the
class; the class self-clears on real `animationend`; interruption (replay while already playing
restarts cleanly, doesn't get stuck active — verified with a 300ms real mirror animation and a
double-click mid-animation); a bubbled child `animationend` doesn't clear the parent
(`target === currentTarget` guard, verified with mismatched-duration real animations so the
bubbled event fires while the parent's own animation is still genuinely mid-playback);
`mergeRefs` attaches to both an object ref and a callback ref, and tolerates `null`/`undefined`
entries; `useShakeOnInvalid` auto-shakes on the false→true transition, does NOT shake a
control already-invalid at mount, does NOT re-shake on unrelated re-renders while staying
invalid, `shakeSignal` re-shakes on repeat failure (only while invalid — ignored while valid); and
the focus-preservation test described above.

Each component's test file adds its own wiring tests (auto-shake-on-transition, no-shake-at-mount,
`shakeSignal` repeat) plus one component-specific test: `checkbox.test.tsx` confirms `ref` and the
internal shake ref land on the same root element; `radio-group.test.tsx` confirms item-level (not
group-level) shaking; `otp-input.test.tsx` confirms the row-level (not per-slot) target;
`input.test.tsx` confirms the addon-mode wrapper-vs-input target split and includes a realistic
"typing in a focused field trips live validation" scenario (not just a button click) as a second,
more true-to-life focus-preservation check. `field.test.tsx` adds the `FieldError`
`motion-enter-up` class check and the bare-`Input`-inside-`Field` self-shake integration test that
justifies the no-double-shake decision above. All pre-existing tests in these six files
(including checkbox/radio-group's fresh touch-target-remediation suites from Phase R) still pass
unmodified.
