## View Transitions — findings + what was wired

**Verified (Context7, Next.js `/vercel/next.js/v16.2.9` — matches this workspace's installed
`next@16.2.9` exactly):** the only App Router mechanism is `experimental.viewTransition: true` in
`next.config.js`
([source](https://github.com/vercel/next.js/blob/v16.2.9/docs/01-app/03-api-reference/05-config/01-next-config-js/viewTransition.mdx)),
which wraps `<Link>` navigations in `document.startViewTransition` and unlocks React's
`<ViewTransition>` + `next/link`'s `transitionTypes` prop. Purely client-side (fires on link
click) — no conflict with `apps/docs`'s `output: 'export'` static export
([source](https://github.com/vercel/next.js/blob/v16.2.9/docs/01-app/02-guides/static-exports.mdx)).
This matches `docs/audits/2026-07-14-system-audit/10-transitions-dev.md §g`'s prior conclusion
that page-level transitions are an app-level (not `packages/ui`) concern, implemented via React's
View Transitions API.

**What was wired (minimal, honest — CSS only, no next.config touched):** `AppShellHeader`
(`page.tsx`) and `AppShellSidebar` (`app-sidebar.tsx`) each carry a
`[view-transition-name:dashboard-shell-header]` / `[view-transition-name:dashboard-shell-sidebar]`
Tailwind v4 arbitrary-property class (a plain CSS custom-ident — not a hex/px literal, passes
`design-lint`'s arbitrary-value contract with no exception needed). Once a consumer enables the
Next flag, this pulls the header/sidebar OUT of the default whole-page root crossfade into their
own stable transition group — since their content is pixel-identical before/after a same-shell
navigation, they read as "not animating" while the rest of the page crossfades. Works with pure
CSS; does not require React's `<ViewTransition>` component.

**Documented, not hacked (per the brief — a next.config flag the block can't carry):**
1. The `next.config.js` flag itself — consumer's responsibility, documented in the mdx with the
   exact snippet.
2. **Layout-hoisting gap, disclosed honestly:** this block's `page.tsx` renders the FULL shell
   itself (mirrors shadcn's own single-route `dashboard-01` shape per the audit's file table) — so
   within THIS block alone, the shell fully unmounts/remounts on navigation to any other route,
   same as any page-scoped tree. The `view-transition-name` styling is real and correct, but for
   the "stays stable" effect to matter, a consumer with multiple routes needs to hoist
   `AppShell`/`AppSidebar`/`AppShellHeader` into a shared `layout.tsx` — documented in the mdx as
   an explicit, deliberate follow-up step, not silently assumed.
3. **Reduced-motion gap in the token layer, disclosed, not fixed (packages/tokens is forbidden
   for this task):** `packages/tokens/src/base.css`'s global `prefers-reduced-motion` reset
   targets `*, ::before, ::after` — verified this does NOT reach the browser's
   `::view-transition-*` top-layer pseudo-element tree (a separate tree that universal selector
   doesn't match). The mdx documents the exact override snippet a consumer needs to add
   (sourced from the `vercel-react-view-transitions` skill's `css-recipes.md`) until that
   token-layer gap is closed as a separate change.

**Not interactively demonstrated:** `apps/docs/next.config.mjs` does not have the flag enabled and
was out of scope to edit for this task, so the crossfade itself could not be shown live in this
repo's own docs site — the `view-transition-name` CSS is present and correct but inert until a
consumer opts in.

## RelativeTime determinism — solution

`RelativeTime` (`packages/ui/registry/ui/relative-time.tsx`) defaults to the live clock and a
`setTimeout` re-render loop. Investigated its props: passing `now` (a fixed epoch-ms reference)
makes `isControlled = now !== undefined` true, which short-circuits both the "X ago" computation
AND the timer effect; `refresh={false}` is an additional explicit belt-and-braces suppression of
the same timer. `recent-activity.tsx` uses `now={DASHBOARD_NOW_MS}` + `refresh={false}`, with
`DASHBOARD_NOW_MS = Date.parse('2026-07-14T09:00:00.000Z')` pinned to `data.json`'s own
`generatedAt` field — every render, at any wall-clock time, produces an identical string. Verified
by a passing test asserting the exact rendered duration string (`'1m 24s'` for the 84000 ms
`task-1042` row).
