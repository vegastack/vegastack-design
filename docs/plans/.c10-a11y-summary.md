## 1. copy-button.tsx (P2-26) — copied-state live region

**What:** Added a visually-hidden `<span className="sr-only" role="status">` inside the button that
renders `copiedLabel` while `copied` is true and is empty otherwise. `aria-live` was **not** added to
the button itself — `role="status"` carries an implicit `aria-live="polite"`, satisfying the
requirement without touching the button's own attributes. The button's `aria-label` swap (Copy ↔
Copied) is unchanged; the live region is the actual announcement mechanism (aria-label changes alone
aren't reliably announced by screen readers).

**Files:** `packages/ui/registry/ui/copy-button.tsx`, `copy-button.test.tsx`.

**Test added:** asserts the `[role="status"]` element is empty before copying, contains "Copied"
immediately after a click, and reverts to empty once the timeout fires.

**Judgment call:** none significant — straightforward per the spec.

## 2. pagination.tsx (P2-27) — enforce disabled PaginationLink

**What:** `PaginationLink` now inspects its own `aria-disabled` prop. When truthy (`true` or `"true"`):
`tabIndex` is forced to `-1` (removed from tab order) and `onClick` is replaced with a handler that
calls `event.preventDefault()` and **never invokes the consumer's `onClick`** (exactly as specified —
not merged/chained). When not disabled, the consumer's own `tabIndex`/`onClick` pass through
unchanged. Updated the JSDoc to describe the enforcement and explicitly note "No extra prop needed on
the consumer side (previously `tabIndex={-1}` had to be set by hand alongside `aria-disabled`)".

Also updated `apps/docs/components/preview/pagination.tsx` (explicitly permitted by this task item):
`paginationFirstPage`/`paginationLastPage` demos now pass only `aria-disabled="true"` (the manual
`tabIndex={-1}` workaround was removed).

**Files:** `packages/ui/registry/ui/pagination.tsx`, `pagination.test.tsx`,
`apps/docs/components/preview/pagination.tsx`.

**Tests added:** one confirming an `aria-disabled` link gets `tabindex="-1"` and a native click never
fires the consumer's `onClick`; one confirming an enabled link keeps its natural tab order (no
`tabindex` attribute) and does fire `onClick`.

**Judgment call / follow-up flagged:** `apps/docs/content/docs/components/pagination.mdx` still has
prose telling consumers to manually add `tabIndex={-1}` — that file wasn't in this task's edit scope
(only the JSDoc + preview.tsx were named), so I left it and spawned a background task
(`task_153a2108`) to fix the stale doc text separately.

## 3. message-scroller.tsx (P1-25) — reduced-motion-aware scroll

**What:** Added an SSR-safe `getPrefersReducedMotion()` / `usePrefersReducedMotion()` hook pair
(`window`/`matchMedia` guarded, live-updates via a `change` listener, not just read-once-on-mount).
Wired it into `MessageScrollerButton`: the vendored `@shadcn/react/message-scroller` primitive's
`Button` defaults its click-triggered scroll to `behavior: "smooth"` (confirmed by reading the
primitive's bundled source — that's the _only_ hardcoded `"smooth"` in the vendored code; the
`useMessageScroller()` hook's `scrollToEnd`/`scrollToStart`/`scrollToMessage` already default to
`"auto"` internally, so they didn't need a wrapper override). Our wrapper now resolves
`behavior = prefersReducedMotion ? "auto" : (consumer's behavior prop ?? "smooth")` and passes that
resolved value to the primitive's `behavior` prop — overriding even an explicit consumer-passed
`behavior="smooth"` while reduced motion is preferred, since accessibility should win over a
component-level default.

**Files:** `packages/ui/registry/ui/message-scroller.tsx`, `message-scroller.test.tsx`.

**Test added:** Module-mocking the vendored primitive didn't work (Vite's `optimizeDeps.include`
pre-bundles `@shadcn/react/message-scroller` per `vitest.config.ts`, so `vi.doMock` doesn't intercept
it — verified by trying it first and seeing the mock ignored). Instead the test forces real scrollable
geometry with explicit inline `style` (not Tailwind classes, since this suite compiles no CSS), mocks
`window.matchMedia` to report `prefers-reduced-motion: reduce`, waits for the button's `data-active`
state, spies on the viewport's real `scrollTo`, clicks the button, and asserts the actual call used
`behavior: "auto"`. Verified the test actually catches a regression by temporarily reverting the fix
and confirming the test fails (`expected 'smooth' to be 'auto'`), then restored the fix.

**Judgment call:** reduced-motion always wins, even overriding an explicit non-default `behavior` prop
from the consumer — documented in the JSDoc.

## 5. emoji-picker.tsx + color-picker.tsx (P2-30) — roving tabindex

**What (both files):** implemented locally per file (no new hooks directory — none existed; per the
task's own instruction not to create one for this). Exactly one grid cell has `tabIndex={0}` at a
time, the rest `-1`. `ArrowLeft`/`ArrowRight` move by 1, `ArrowUp`/`ArrowDown` move by the column
count, `Home`/`End` jump to the first/last item. `onKeyDown` lives on the grid container; click
behavior (`onClick`) is unchanged; a matching `onFocus` on each cell keeps the roving index in sync if
focus moves by some other means (e.g. mouse click).

- **color-picker.tsx:** single flat grid, `columns` prop (default 7) drives the arrow-down/up stride.
  Active index initializes to the currently-selected color (`value`) when present, else the first
  swatch — so reopening the popover lands keyboard focus on the current selection.
- **emoji-picker.tsx:** the grid is visually split into per-category `role="group"` sub-grids (7
  columns each, `GRID_COLUMNS` constant), but I treated the **whole visible set as one continuous
  roving-tabindex grid** (flattened across categories) rather than one roving region per category —
  category headings are visual grouping only. This means ArrowDown/Up can cross a category boundary,
  which reads as more natural than getting stuck at each category's edge. Noted as the deliberate
  choice in the JSDoc.
- **Home/End judgment call (both files):** jumps to the first/last item in the **entire** grid, not
  row-local — noted in both JSDocs as the deliberate choice (row-relative would need each row's
  start/end offset, not needed at these grid sizes).
- Active index re-clamps whenever the visible set shrinks (color list changes, or emoji search
  narrows results) so it never points past the end.

**Files:** `packages/ui/registry/ui/emoji-picker.tsx`, `emoji-picker.test.tsx`,
`packages/ui/registry/ui/color-picker.tsx`, `color-picker.test.tsx`.

**Tests added (each file):** one asserting only the expected cell has `tabindex="0"` (others `-1`);
one asserting `ArrowRight` moves both DOM focus and the `tabindex="0"` marker to the next cell.

## 6. alert-dialog.tsx (P2-32) — AlertDialogAction loading

**What:** Added `loading?: boolean` to `AlertDialogActionProps`, passed straight through to the
internal `Button` (`<Button ... loading={loading} />` inside the `render` prop of
`BaseAlertDialog.Close`). This reuses `Button`'s existing `loading` behavior verbatim: spinner,
`aria-busy`, and `focusableWhenDisabled` (Base UI marks it `aria-disabled="true"` rather than the
native `disabled` attribute, so the control stays focusable/discoverable while busy). Base UI's own
`Button` `onClick` handler short-circuits on `disabled` before calling anything else, so a click while
`loading` never reaches the consumer's `onClick` **or** Base UI's `Close` dismiss handler — the dialog
stays open until `loading` is set back to `false`. JSDoc explains this and suggests the
`onClick={async () => { setLoading(true); await doDelete(); setLoading(false); }}` pattern.

**Files:** `packages/ui/registry/ui/alert-dialog.tsx`, `alert-dialog.test.tsx`.

**Test added:** opens the dialog with `<AlertDialogAction loading onClick={onConfirm}>`, asserts
`aria-busy="true"`, `data-loading=""`, and `aria-disabled="true"` (not the native `disabled`
attribute — see above), then does a native `.click()` (bypassing Playwright's actionability gate,
which treats `aria-disabled="true"` as "not enabled") and confirms `onConfirm` never fires and the
dialog stays open.

**Judgment call:** initially asserted the native `disabled` DOM property, which is wrong — Base UI
uses `aria-disabled` (not `disabled`) when `focusableWhenDisabled` is set (which `Button` does
whenever `loading` is true), specifically so a loading button stays keyboard-discoverable. Confirmed
by reading `@base-ui/react`'s `useButton`/`useFocusableWhenDisabled` source, then fixed the test.

## 7. field-inline.tsx (P2-33) — disabled / readOnly / error

**What:** Added three props:

- **`disabled`** — blocks `startEdit()` (guarded inside the callback itself, not just via missing
  handlers, so it's defended even if something else calls it). Display root keeps `role="button"`
  (stays discoverable/consistent with a real disabled control) but gets `aria-disabled="true"`,
  `tabIndex={-1}` (removed from tab order — mirrors a native disabled `<button>`, since a `role="button"`
  span has no native disabled semantics), and
  `aria-disabled:pointer-events-none aria-disabled:opacity-(--opacity-dim)` (mirrors the exact
  Tailwind pattern already used by `pagination.tsx`'s disabled links).
- **`readOnly`** — renders as plain, non-interactive text: no `role`, no `tabIndex`, no
  click/keydown handlers, no hover affordance, and not dimmed (distinguishing it from `disabled`).
- **`error`** (string) — in edit mode, the `Input` gets `aria-invalid={true}` (which triggers
  `input.tsx`'s own built-in `aria-invalid:border-destructive/(--alpha-tint-border)` styling — no
  extra class needed in `field-inline.tsx` itself) plus `aria-describedby` pointing at a
  `role="alert"` error `<span>` styled `text-sm leading-normal text-destructive-text` (the same
  classes `field.tsx`'s `FieldError` uses). The error text renders in **both** display and edit mode
  whenever `error` is set (a `React.useId()`-generated id links the two).
- If `disabled`/`readOnly` flips to `true` while mid-edit, a `useEffect` cancels the edit the same way
  `Escape` does (revert the draft, skip `onCommit`) instead of leaving an edit open on a field that
  just became uneditable.
- The component's return value became a `<>...</>` fragment (control + optional error text) instead of
  a single element in both branches — the `ref` still attaches directly to the control (span or
  input), so the documented "ref forwards to the display span / edit input" contract is unchanged and
  the existing ref tests still pass unmodified.

**Files:** `packages/ui/registry/ui/field-inline.tsx`, `field-inline.test.tsx`.

**Tests added:** `disabled` blocks entering edit mode (native `.click()` used to bypass Playwright's
`aria-disabled` actionability gate) and doesn't call `onCommit`; `readOnly` has no `role`/`tabindex`
and clicking does nothing; `error` shows the alert text in display mode and marks the edit-mode input
`aria-invalid` + `aria-describedby` pointing at matching alert text.

**Judgment call:** `disabled` keeps `role="button"` (just non-operable + `aria-disabled` + out of tab
order) while `readOnly` drops button semantics entirely — treating them as two different "flavors" of
non-editable rather than collapsing them into one state, since the task described them with
distinctly different behaviors (blocked-but-discoverable vs. plain-text-no-affordance).
