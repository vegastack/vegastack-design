## 1. `page-header.tsx` — `<header>` landmark

Root changed from `<div data-slot="page-header">` to `<header data-slot="page-header">`. This is a
banner landmark whenever `PageHeader` isn't nested inside `<article>`/`<aside>`/`<main>`/`<nav>`/
`<section>` — no extra ARIA needed, `<header>` gets the role for free per HTML-AAM.

- Type changed `Omit<React.ComponentPropsWithRef<'div'>, 'title'>` → `Omit<React.ComponentPropsWithRef<'header'>, 'title'>`.
  `header` has no dedicated DOM interface, so a ref lands as a plain `HTMLElement`, not
  `HTMLDivElement`.
- Searched the repo for other consumers/ref-typings of `PageHeader` outside the allowed file set —
  none found (only `preview/page-header.tsx` and the test file reference it, both updated/allowed).
- Updated `page-header.test.tsx`'s `'forwards ref to the root element'` test:
  `React.createRef<HTMLDivElement>()` + `toBeInstanceOf(HTMLDivElement)` →
  `React.createRef<HTMLElement>()` + `toBeInstanceOf(HTMLElement)` + `tagName === 'HEADER'`
  (the old assertion would have failed — a `<header>` node is not `instanceof HTMLDivElement`).
- Added a new test asserting `getByRole('banner')` resolves and carries `data-slot="page-header"`.

## 2. `page-header.tsx` — title truncation via `TruncatedText`

**Decision — the h1-wraps-TruncatedText shape** (not `as="h1"` — `TruncatedText`'s `as` prop only
offers `'span' | 'p' | 'div'`, no heading level): kept the `<h1 data-slot="page-header-title">` as
the outer element (so it stays the one accessible heading, unaffected by whether the title
happens to be truncated) and nested `<TruncatedText>{title}</TruncatedText>` inside it:

```tsx
<h1 data-slot="page-header-title" className="min-w-0 text-h2 text-foreground">
  <TruncatedText>{title}</TruncatedText>
</h1>
```

- Removed the old hardcoded `truncate` class from the `<h1>` — `TruncatedText`'s own `block
truncate` (on its inner `<span data-slot="truncated-text">`) now owns clipping, tooltip-on-hover/
  focus, keyboard-focusability when clipped, and the touch tap-to-toggle disclosure — all for free,
  all already audited/tested in `truncated-text.tsx`.
- **Bug fix required for the wiring to actually engage**: added `min-w-0` to the `<h1>`. It's a
  flex item inside `<div className="flex items-center gap-1">` (back button, title, favorite
  star); a flex item's default `min-width: auto` is content-based and would have stopped the title
  from ever shrinking past its own content width — meaning `TruncatedText`'s
  `ResizeObserver`/`scrollWidth`-vs-`clientWidth` measurement would never see an overflow, so the
  ellipsis/tooltip would never engage no matter how long the title got. This was latent even
  before this change (the old `truncate` class on the h1 had the exact same problem) — now fixed.
- `title: React.ReactNode` (PageHeaderProps) → `TruncatedText`'s `children: React.ReactNode` — types
  line up directly, no cast needed.
- **`registryDependencies` to add for `page-header`** (currently `["@vegastack/button",
"@vegastack/icon-button"]` in `packages/ui/registry.json`): add `"@vegastack/truncated-text"`.
  Not applied here (registry.json is out of scope / `registry:build` wasn't run) — flagging for the
  next `registry:build` pass.
- Docs: added a "Long title" example (`pageHeaderLongTitle` preview, wrapped in a `max-w-sm`
  container so it reliably overflows regardless of viewport) + updated Anatomy/Accessibility prose
  in `page-header.mdx`.

## 3. `breadcrumb.tsx` — responsive overflow collapse

**Decision — static (a) shipped, dynamic (b) evaluated and deliberately deferred** (documented
in-component and in `breadcrumb.mdx`). Rationale: `TruncatedText`'s `ResizeObserver` measures one
text node's single-axis overflow; collapsing a _set_ of breadcrumb items would need a
resize-and-recompute loop trying successive collapse states until the row fits — real risk of
visible layout thrash and SSR/hydration mismatch for a component that sits at the top of the page.
An honest, deterministic `maxItems` API beats a flaky measurer. `BreadcrumbList` keeps `flex-wrap`
as the literal no-collapse fallback (unchanged).

Kept `BreadcrumbEllipsis` **exactly as it was** — still decorative, still exported, the existing
`breadcrumbEllipsisMenu` manual-composition preview still renders. Added two new exports on top:

- **`BreadcrumbCollapsed`** — the building block. Pairs the decorative `BreadcrumbEllipsis` glyph
  with a `DropdownMenuTrigger` (`aria-label`, default `"Show hidden breadcrumbs"`,
  `data-slot="breadcrumb-collapsed-trigger"`) and a `DropdownMenuContent` of `DropdownMenuItem`s.
  Takes `items: BreadcrumbSegment[]`; each renders `render={item.render ?? <a href={item.href} />}`
  — a **real anchor** inside the menu (confirmed via Base UI's `MenuItem` source: it always reports
  `role="menuitem"` regardless of the underlying rendered element, but the DOM node is a genuine
  `<a href>`, so middle-click/"open in new tab"/crawlers keep working). This formalizes the exact
  pattern already shipped in the `breadcrumbEllipsisMenu` preview.
- **`BreadcrumbTrail`** — the primary ergonomic API. `items: BreadcrumbSegment[]` +
  `maxItems?: number` + `itemsAfterCollapse?: number` (default `1`) + `collapsedLabel?: string`.
  Renders a `BreadcrumbList`; when `items.length > maxItems`, the first item and the last
  `itemsAfterCollapse` items stay flat, everything between renders inside one `BreadcrumbCollapsed`.
  Purely a function of `items.length` — no DOM measurement, so it's SSR-safe by construction.
  Without `maxItems`, behaves identically to composing `BreadcrumbList` by hand (flex-wrap).
- **`BreadcrumbSegment`** — the shared item type (`label`, `href`, `render`, optional `key`).

**Type note**: `BreadcrumbSegment.render` is typed `useRender.RenderProp<any>`, not the default
`useRender.RenderProp` (= `RenderProp<Record<string, unknown>>`). The same segment has to feed
either `BreadcrumbLink`'s `render` (state defaults to `Record<string, unknown>`) or
`DropdownMenuItem`'s `render` (state is Base UI's `MenuItemState = { disabled, highlighted }`,
which has no index signature and so isn't assignable to `Record<string, unknown>`) — those two
callback shapes aren't mutually assignable under `strictFunctionTypes`, and `<any>` is the correct,
narrow escape hatch (documented inline) rather than loosening either component's own `render` prop.
