## Token-only theming — design + the THEMES/ChartStyle removal

shadcn/ui's reference `Chart` injects a `<style dangerouslySetInnerHTML>` keyed off a
`THEMES = { light: '', dark: '.dark' }` selector map, and lets `ChartConfig` entries carry a
`{ light, dark }` hex/oklch pair (`ChartStyle` renders `[data-chart=<id>] { --color-x: <hex> }` once
per theme, scoped by a `React.useId()`-generated `data-chart` attribute).

VegaStack's chart palette is **already theme-split at the token layer** — `--chart-1`…`--chart-8` are
defined once in `packages/tokens` for both `:root` and `.dark` (confirmed:
`packages/tokens/dist/theme.css:46-53` light, `:170-177` dark, plus the `@theme inline` bridge
`--color-chart-N: var(--chart-N)` at `:280-287`). So here:

- `ChartConfig.color` is TOKEN-ONLY: `ChartColorToken` (`'chart-1'`…`'chart-8'`) or the literal
  `` `var(--${ChartColorToken})` `` string — never a hex/oklch literal, never a `{ light, dark }` pair.
- `ChartContainer` resolves each configured entry to a `--color-<key>: var(--chart-N)` custom property
  set **directly in its own `style` prop** on the `data-slot="chart"` div — no injected `<style>` tag,
  no `React.useId()`, no `data-chart` id-scoping.
- This is not merely simpler — it's *more correct*: the CSS var is scoped by ordinary DOM ancestry
  (every descendant of the container reads whatever `--color-<key>` that container declares), not a
  global id-attribute selector, so multiple chart instances never need an id to avoid colliding. And
  it stays theme-reactive for free: `var(--chart-N)` re-resolves against whichever theme scope
  (`:root` / `.dark`) the container sits under at read time — there is nothing chart-specific left
  needing to "know about" light/dark.
- `ChartStyle` (the shadcn export) is deleted entirely. `THEMES` is deleted entirely.

This is recorded as the intended design in `chart.tsx`'s file-level JSDoc (not hedged as a
simplification-with-caveats).

## Recharts 3.9.2 API notes / deviations from the shadcn reference

Installed version is `recharts@3.9.2` in both `packages/ui` and `apps/docs` (task said "targets
recharts 3.8" — repo actually has 3.9.2, a compatible superset; verified via `node_modules` `.d.ts`/
`es6` source, not guessed):

1. **`accessibilityLayer` already defaults to `true`** on every Cartesian/Polar chart
   (`defaultCartesianChartProps.accessibilityLayer = true` in
   `node_modules/recharts/es6/chart/CartesianChart.js`). We still pass it explicitly in every example
   (house requirement) so it reads as intentional and survives a future default change.
2. **What `accessibilityLayer` actually does** (`node_modules/recharts/es6/container/RootSurface.js`):
   when on, the root `<svg>` gets `role="application"` + `tabIndex={0}`; Recharts' own layer wires
   arrow-key data-point navigation. `ChartContainer` deliberately does **not** add `role="img"` — that
   would collide with Recharts' own `role="application"`.
3. **Dropped the shadcn reference's attribute-value CSS hack** for grid/cursor/dot colors
   (`[&_.recharts-cartesian-grid_line[stroke='#ccc']]:stroke-border/50` and siblings). Two reasons,
   both verified against the installed source: (a) it embeds hex literals (`#ccc`, `#fff`) that this
   repo's `design-lint` bans unconditionally — `hex-color` rule fires on ANY line containing the
   pattern, comments aside; (b) it's brittle — `CartesianGrid` (`stroke: '#ccc'`,
   `es6/cartesian/CartesianGrid.js:270`), the `BarChart`/Line hover cursor (`stroke: '#ccc'`,
   `es6/component/Cursor.js:94`), and dot defaults (`stroke: '#fff'`, `es6/cartesian/Line.js:126`) are
   internal implementation details, not part of Recharts' public API contract. Kept only the
   **class-based** (not attribute-value) descendant overrides that are hex-free and stable:
   axis-tick label color (`fill-muted-foreground`) and outline resets on Recharts' own SVG layers.
   Documented the replacement pattern (set `stroke`/`fill`/`cursor`/`dot` directly on the primitive,
   with a token) in the file JSDoc, the MDX "Styling Recharts primitives" section, and every preview
   demo.
4. **`ChartTooltipContentProps` / `ChartLegendContentProps` had to become `type` intersections
   (`&`), not `interface extends`** — `tsc` rejects `interface X extends A, B` when `A`/`B` declare a
   same-named member with incompatible signatures (TS2320), which happens here (`ComponentProps<typeof
   Tooltip>` vs `ComponentProps<'div'>`, and `ComponentProps<'div'>` vs `DefaultLegendContentProps`
   both collide, e.g. on `onClick`). Reference source (a plain `.tsx`, not type-checked in isolation
   the same way) sidesteps this by only ever using `type = A & B & C`, which we now also do
   throughout — confirmed clean via `npx tsc --noEmit` in `packages/ui`.
5. `RechartsPrimitive.DefaultTooltipContentProps<TValue, TName>`'s `Payload` type requires
   `graphicalItemId: string` (not present in older recharts 2.x-era `Payload` shapes) — reflected in
   the test fixtures.
6. `ResponsiveContainer`'s `children` prop type is a plain `ReactNode` (not a function-render-prop) in
   this version — `ChartContainer`'s JSDoc says "child", not "function-or-element child".
7. **`Tooltip`'s `defaultIndex` prop** (a real recharts 3 feature, not a workaround) pins the tooltip
   open at a fixed data index with zero hover/interaction — used in the `chartDemoTooltipVariants`
   preview to make a 3-up dot/line/dashed comparison deterministic for VRT screenshots, instead of
   simulating a hover.
