## STEP 1 — Scope mechanism (CX-10)

**Design.** `.vs-marketing` — a CSS class in `packages/tokens/src/utilities.css` that re-declares
the same semantic custom properties `.dark` sets (`--background`, `--foreground`, `--card`,
`--card-foreground`, `--popover`, `--popover-foreground`, `--primary(-hover/-active/-foreground)`,
`--secondary(-foreground)`, `--muted(-foreground/-foreground-faint)`, `--accent(-foreground)`,
`--border`, `--input`, `--ring`, `--overlay`, `--brand`), scoped to a class instead of gated on the
page-root `.dark` class. `MarketingSurface` (`packages/ui/registry/ui/marketing-surface.tsx`) is a
thin polymorphic component (`useRender`, default `<div>`) that applies `vs-marketing bg-background
text-foreground`. `Terminal` self-applies the same class so an install snippet reads dark even
embedded in a light docs page, without a `MarketingSurface` wrapper.

**Why component-level CSS, not a 3rd build-pipeline selector.** The brief said "prefer
component-level scoping" and scoped my tokens ownership to `utilities.css`/`global.css`
specifically for this mechanism — `packages/tokens/build-tokens.mjs` and `tokens/*.json` were left
alone. The values in `.vs-marketing` are therefore a MANUALLY-SYNCED literal duplicate of
`semantic.dark.tokens.json`'s resolved oklch() output (same precedent as the existing `overlay`
scrim token — "one sanctioned literal duplication"), with a comment flagging the principled fix
(a 3rd Style Dictionary platform run, selector `.vs-marketing`) for whoever owns the tokens build
pipeline next. If `semantic.dark.tokens.json` changes, `.vs-marketing` needs a matching edit.

**Portal limitation** — documented in both the CSS comment and `MarketingSurface`'s JSDoc: Base UI
floating surfaces portal to `<body>`, outside any `.vs-marketing` subtree, so a portaled surface
opened from inside a `MarketingSurface` inherits the PAGE theme. Marketing surfaces rarely need
portals; the docs-home dogfood doesn't use one.

**Prototype.** Built directly on the docs-home hero (see STEP 3) — `MarketingSurface render={<main
/>}` wraps the ENTIRE home page (not just the hero band), with `/docs/*` staying the light-primary
product surface. Rationale: the docs-home page structurally IS a marketing landing page (the
audit's "cross-temperature bridge" — dark marketing → light product — happens once, at the
home→docs nav transition, matching how the 12-company survey's closest analogs keep one page = one
temperature rather than alternating within a single scroll).

**Self-review against the spec checklist (before moving to STEP 2):**
- Dark warm ground, independent of `.dark` — yes, verified by rendering `MarketingSurface` on a
  page with no `.dark` ancestor (docs-home has none) and confirming `bg-background` resolves to
  the dark oklch value via the scoped class (unit-tested: `marketing-surface.test.tsx` asserts the
  `vs-marketing` class is present; the actual CSS resolution is a visual/VRT concern out of my
  local test harness's reach — no compiled CSS in `packages/ui`'s fast unit tests).
- Display type — `SectionHeader` uses the tokenized `text-display-sm/md/lg/xl` ladder (already
  shipped, tracking baked in); the hero uses `size="xl"`.
- Mono eyebrow — `SectionHeader`'s eyebrow is `font-mono text-mono-label uppercase`.
- ONE phosphor accent — see the accent-budget count in STEP 3.
- Sharp CTA — the `cta` Button variant (`rounded-(--radius-sharp)`).

### The 10px FIG-annotation question

The spec permits (not requires) an optional 10px floor for FIG-style annotations ("12px floor, 10px
only for FIG-annotations"). No token below 12px (`text-mono-label`) ships today, and adding one
would mean editing `packages/tokens/tokens/semantic.tokens.json` + running the tokens build — both
outside this phase's scoped tokens ownership (limited to `utilities.css`/`global.css` for the scope
mechanism specifically). `FigureFrame`'s caption intentionally stays at the 12px floor instead of
inventing an unscoped one-off `text-[10px]` (which `design-lint`'s arbitrary-value rule would also
reject). Documented in the component, the mdx page, and `design.md`'s new Brand & Marketing
section. Flagged as a real follow-up, not silently dropped.

### A real bug found and fixed along the way

`buttonVariants({ variant: 'cta' })` combined with `text-mono-label text-brand` and the base
string's `text-base` produced a broken render: the CTA button silently lost `text-mono-label`
entirely. Root cause: `@vegastack/utils`'s `cn()` (`packages/utils/src/index.ts`) extends
`tailwind-merge` to recognize the design system's custom font-size tokens as a `font-size` class
group (`text-h1`…`text-h4`, `text-label*`, `text-code*`, `text-display-*`) — its own comment
documents this exact failure mode happening once already (T1/MarkdownView). `text-mono-label`
was never added to that list, so `tailwind-merge` misclassified it as a `text-color` utility,
where it collided with — and lost to — the later `text-brand` class in the same string. Fixed by
adding `'mono-label'` to the existing extension list (one line, same pattern, same file) and
rebuilding `packages/utils` (`pnpm run build` — `dist/index.js`/`.d.ts`). Verified: the full
`packages/ui` suite (1120 tests) and `packages/utils`'s own tests still pass after the fix — no
regressions from touching a shared utility.

**A real RSC bug found and fixed**: the first draft called `buttonVariants({...})` directly inside
`page.tsx` (a Server Component) for the two `Link`-styled CTAs. `buttonVariants` is exported from
`button.tsx`'s `'use client'` module — Next.js's RSC boundary allows RENDERING a client
component's JSX from server code, but not CALLING an arbitrary function export from that module;
`next build`'s static export failed with `Attempted to call buttonVariants() from the server but
buttonVariants is on the client`. Fixed by switching to `<Button variant="cta" render={<Link
href="..." />} nativeButton={false}>` — composing `Button` as JSX (Base UI `render`) instead of
calling its helper function, which is also the pattern `Button`'s own JSDoc already documents for
navigation ("style an anchor with `buttonVariants`... " — via `render`, since a direct function
call turned out to be the RSC-illegal half of that sentence). `page.tsx` also imports
`GeistPixelSquare` directly (a next/font local-font export, safe to import in any Server Component
module — it doesn't itself call the font loader, `geist/dist/pixel.js` does that once at ITS OWN
module scope).
