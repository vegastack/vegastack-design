## Mechanism chosen (Task 1 investigation)

Base UI's `Combobox.Root` supports an `inline` prop: _"Whether the list is rendered inline without
using the component's own popup. Specify `open` unconditionally in conjunction with this prop."_
`Command` = `<Combobox.Root inline open modal={false}>`. This renders the list as part of normal
layout flow (no floating popup), which is exactly the palette shape. `CountrySelect`/`RegionSelect`
instead use the **normal** (non-inline) Combobox mode with the search input living _inside_
`ComboboxContent` (`inputInsidePopup`), which is Base UI's own "Select-style" pattern (verified:
this flips the trigger's role to `combobox`/`aria-haspopup="dialog"` and disables single-mode's
"fill input with the selected label" behavior).

## API surface (breaking changes from cmdk)

`Command`, `CommandDialog`, `CommandInput`, `CommandList`, `CommandEmpty`, `CommandLoading`,
`CommandGroup`, `CommandItem`, `CommandSeparator`, `CommandShortcut` — same export names. NEW:
`useCommandFilteredItems` (replaces `useCommandState`, which is dropped — no equivalent internal
store).

**DATA-DRIVEN, mandatory.** Base UI's Combobox only filters — and drives `CommandEmpty` — off a
query-filtered `items` array on the root (verified in source: `filteredItems` is unconditionally
`[]` when no `items` prop is given; there's no "static children, no items" fallback the way cmdk
worked). `Command` takes `items` (flat array, or an array of `{ heading, items }` groups).
`CommandList` accepts a function child for flat rendering (Base UI auto-wraps it in a
`Combobox.Collection`); grouped rendering calls `useCommandFilteredItems()` + maps to
`CommandGroup`s (mirrors combobox.tsx's own `useComboboxFilteredItems` pattern exactly, including
its "items must be the FILTERED result, not the original array" caveat).

**Anatomy change.** `CommandEmpty`/`CommandLoading` (Base UI `role="status"`) now render as
**siblings** of `CommandList` (`role="listbox"`), not its children — nesting them (the old cmdk
build's structure) trips `aria-required-children` (a listbox only owns `option`/`group`). This is
the fix Base UI's own `ComboboxContent` docs prescribe. The old suppressed-rule test in
`command.test.tsx` ("no a11y violations — loading") now passes for real, no suppression.

**Dropped:** `useCommandState` (no equivalent). Per-item `keywords`/`forceMount` cmdk props (no
Base UI equivalent — see "How dropped props are now expressed" below).

## Findings verified via vitest-browser (not guesses)

1. **`autoHighlight="always"` is required to match the old first-item-highlighted default.**
   Base UI's own public `Combobox.Root` TS type narrows `autoHighlight` to `boolean` (dropping the
   `'always'` literal that the internal `AriaCombobox` supports and the JSDoc lists), but the
   runtime honors it unvalidated — verified: without it, the first `ArrowDown` press only
   highlights item 0 (nothing was highlighted); with `autoHighlight="always"`, item 0 is
   pre-highlighted on mount and the first `ArrowDown` correctly moves to item 1, matching cmdk.
   `Command` defaults `autoHighlight="always"`, cast around the narrower public type.

2. **`role="combobox"` never gets `aria-expanded` in `inline` mode — a real, consistent a11y gap,
   not a timing race.** Reproduced via a 5x repeat loop with a hard assertion (`toBe('true')`)
   before concluding it wasn't flaky. `CommandInput` now hardcodes `aria-expanded="true"` (Command
   is architecturally always "expanded").

3. **Base UI's Combobox does not skip `disabled` items during arrow-key navigation.** Confirmed in
   source: `AriaCombobox.mjs` hard-codes `disabledIndices: EMPTY_ARRAY` for its floating-ui
   list-navigation — there is no prop to opt into skip-in-navigation. A `disabled` item is still
   inert (`onClick`/`onSelect` bails, matching cmdk), it's just reachable by arrow keys. Documented
   in `CommandItem`'s JSDoc, the mdx States section, and the characterization test's DEVIATION.

4. **`Combobox.Item.onClick` is cmdk's `onSelect` equivalent** — its own doc comment: _"fires when
   clicking the item with the pointer, as well as when pressing Enter with the keyboard if the
   item is highlighted."_ Verified via source too: `ComboboxInput`'s own Enter-key handler
   (`if (event.which === 229) return;` then `listItem.click()`) directly checks IME `keyCode 229`
   before committing — meaning `CommandItem`'s `onSelect` (wired straight to `onClick`) gets IME
   safety for free, no extra code needed.

5. **Base UI cleanly separates "highlighted" (keyboard/pointer cursor, `data-highlighted`,
   `activeIndex`) from "selected" (a persisted choice, `aria-selected`/`data-selected`,
   `selectedValue`) — cmdk conflated these into one `data-selected` attribute.** `CommandItem`
   styles off `data-highlighted` (matching cmdk's old moving-cursor semantics). `Command`'s
   `value`/`onValueChange` (same prop names as before, kept for continuity) now maps to Base UI's
   native SELECTED value, not highlight — and, verified via source, a controlled `value` is never
   retroactively synced to the highlight while the list stays open (`syncSelectedIndex` in
   `AriaCombobox.mjs` early-returns whenever `open` is true, which is always, since Command is
   `inline open`). Reinterpreted as the more idiomatic mapping for a greenfield API; the one
   characterization test that cared about this now asserts selection, not highlight.

6. **`CountrySelect`/`RegionSelect`'s trigger label must NOT go through combobox.tsx's own
   `ComboboxTrigger`.** That component always wraps its `children` in Base UI's `Combobox.Icon`,
   which is unconditionally `aria-hidden` (verified in `ComboboxIcon.mjs`) — correct for an
   icon-only trigger, but it would silently strip the flag+name label from the accessibility tree.
   Both components instead compose `@base-ui/react/combobox`'s `Combobox.Trigger` directly
   (`render={<Button/>}`), with `ComboboxValue` (not hidden) and the chevron as plain siblings.

## How dropped cmdk props are now expressed

- **`keywords`** (per-item alias terms): fold into the item's own data (`{ value, label, keywords }`)
  and match them from a custom `filter` on `Command` — `docs/plans/.x1-command-summary.md`'s
  sibling test/preview/mdx all do this (`command.test.tsx`'s "keywords beyond the visible label"
  test, the docs preview's `commandAdvanced`).
- **`forceMount`** (keep an item mounted regardless of the query): compose it as a plain static
  sibling OUTSIDE the filtered `CommandGroup`/`useCommandFilteredItems` result — there is no
  per-item flag, since items only ever come from the query-filtered `items` array. Demonstrated in
  `command.test.tsx`'s "a statically-composed item stays mounted while filtering" test.
- **`shouldFilter={false}`**: Base UI's own `filter={null}` escape hatch (disables filtering
  entirely, all items stay mounted) — same test coverage, renamed.

## Deviations recorded (characterization spec, `command.characterization.test.tsx`)

9 of 11 tests are behaviorally unchanged (same assertions, same expected values) after two
structural (not behavioral) edits to the shared `Palette` fixture and the `selectedItem()` helper
(items-driven composition; the helper now queries `data-highlighted` instead of `data-selected`/
`aria-selected`, per finding #5). Two tests have genuine behavioral deviations, each with an
inline `// DEVIATION:` comment:

- **`disabled-skip`** — asserts the item IS reachable (`Beta`, not skipped), per finding #3, a
  confirmed Base UI limitation, not a design choice.
- **`controlled value`** — asserts the SELECTED item (`aria-selected`), not the highlighted one,
  per finding #5's reinterpretation.
- (A third structural-only change: the `async` test now feeds items through `items` reactively
  instead of static late-mounted children, since `items` is mandatory for filtering — same
  end-to-end behavior proven, different mechanism.)

`command.test.tsx` (regular suite) was fully rewritten for the new implementation; every
DEVIATION is commented at its call site (grouped rendering via `useCommandFilteredItems`, the
`keywords`→custom-`filter` port, the `forceMount`→static-sibling port, `shouldFilter`→`filter:
null`, and the loading-state a11y fix landing "for real" instead of via suppression).

## Task 2 — `country-select.tsx` / `region-select.tsx`

Both refactored into thin data-fed `Combobox` compositions; **public API unchanged** (props,
`COUNTRIES`/`getCountryByCode`/`REGIONS_BY_COUNTRY`/`getRegionsByCountry`/`hasRegions`, flag
rendering, region's free-text fallback for countries with no subdivisions, button trigger +
`ChevronsUpDown`). `RegionSelect`'s "re-selecting the already-selected state clears it" toggle UX
(no Base UI equivalent for single-select) is now driven by a manual per-item `onClick` that
computes the toggle directly, while `Combobox`'s root `onValueChange` is deliberately left unwired
to avoid a second, conflicting change signal — `Combobox`'s `value` is still fully controlled from
this component's own state, so the built-in `aria-selected` indicator (and its trailing checkmark)
stay correct. Added `autoHighlight` to both (a genuine UX gap otherwise: type-then-Enter with an
exact single match wouldn't select anything without it — caught by
`region-select.test.tsx`'s existing "keyboard: typing then Enter" test).

**Test deviations (3 of 13 `country-select.test.tsx` tests, 0 of 18 `region-select.test.tsx`
tests):** the trigger's accessible role changed from an implicit `<button>` ("button") to explicit
`role="combobox"` (Base UI's Select-style pattern — the same role `region-select.tsx` already used
even before this refactor, so it's a consistency fix, not a regression). `getByRole("button")` →
`getByRole("combobox")` in the 3 affected tests, each with a `// DEVIATION:` comment.
`region-select.test.tsx` needed **zero** structural changes — its existing `role="combobox"`
assertions already matched.

`registry.json`: both items now list `@vegastack/combobox` + `@vegastack/button` (and `input` for
region-select) in `registryDependencies`, dropped `@vegastack/popover` + `@vegastack/command`, and
added `@base-ui/react@^1.6.0` to `dependencies` (both now import `Combobox as BaseCombobox` from
`@base-ui/react/combobox` directly, alongside `@/components/ui/combobox`, for the reason in
finding #6 above).
