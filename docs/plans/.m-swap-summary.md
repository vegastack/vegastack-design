Scope: `packages/ui/registry/ui/{copy-button,auto-save-input,password-input,split-button}.tsx` (+ `.test.tsx`). No other files touched — `apps/docs/components/ui/*`, `apps/docs/public/r/*`, `apps/docs/content/docs/*.mdx`, and `apps/docs/components/preview/*.tsx` were already dirty from prior work before this pass started; none of them needed changes for this task (no docs/demo copy references the swap behavior, so nothing to update there).

## Headline finding: `motion-check-draw` is not reachable through `lucide-react`'s public API

Investigated (read `node_modules/.pnpm/lucide-react@1.21.0.../dist/esm/createLucideIcon.mjs` and `Icon.mjs`, and `check.mjs`):

- `createLucideIcon` builds each icon as `forwardRef(({className, ...props}, ref) => createElement(Icon, {..., ...props}))` — consumer props (`{...rest}` in `Icon.mjs`) are spread **only onto the root `<svg>` element**.
- The inner `<path>` is built directly from the icon's fixed `iconNode` array (`iconNode.map(([tag, attrs]) => createElement(tag, attrs))`) with **no prop merge** — there is no way to get `pathLength={1}` (or any other attribute) onto the generated `<path>` by passing props to `<Check />`.
- The raw path data (`__iconNode`) is exported from the per-icon module (`check.mjs`) but **not** re-exported from the package's public entrypoint (`lucide-react.mjs` only re-exports the icon components), and there's no `exports` map restriction in `package.json` stopping a deep import — but a deep import into `lucide-react/dist/esm/icons/check.mjs` would be an unsupported, version-fragile internal path.
- The remaining alternative — a small local component rendering the check `<path>` directly as inline SVG — is explicitly barred by the AGENTS.md icon house rule: _"Icons: ONLY lucide-react ... via Icon/BrandIcon. No other icon libraries, no inline `<svg>` as an icon."_

**Decision:** both `copy-button.tsx` and `auto-save-input.tsx` fall back to `motion-pop-in` for their success `Check` icon instead of `motion-check-draw`, per the task's own documented fallback path. This is called out in an inline comment at each icon swap site (not just here) so a future agent doesn't rediscover the same dead end.

## Per-component treatment

### `copy-button.tsx`

- Copy → Check swap: keyed presence (`key="copy"` / `key="check"`) + `motion-pop-in` on **both** icons (symmetric — the reverse Check → Copy swap after the timeout also gets an arrival animation).
- `copiedLabel` text: **no swap exists to animate.** `CopyButton` never renders visible text (`children` is omitted from its prop type) — the only text is the `sr-only role="status"` live region, which is visually hidden. Motion on a node no sighted user ever sees is meaningless, and the live region's announcement mechanism is the `aria-live`/`role="status"` semantics, not an entrance animation. Documented in a comment above the icon swap; deliberately left unanimated.

### `auto-save-input.tsx`

- `saving` → `saved` → `error` status icon swap: keyed presence (`key="saving"` / `"saved"` / `"error"`) on the `Spinner`/`Check`/`X`.
- `Check` (saved) = `motion-pop-in`, same choice as copy-button, for visual consistency between the system's two "success check" moments.
- `X` (error) = `motion-pop-in`, per the task brief.
- `Spinner` (saving) = keyed only, no added animation class — it already has its own continuous `animate-spin`; layering an arrival pop on top wasn't in the brief and would be redundant motion on an element that's already visually active.
- Status text (`sr-only` span, "Saving"/"Saved"/"Save failed"): same reasoning as copy-button — visually hidden, so left unanimated (documented inline).

### `password-input.tsx`

- Eye ↔ EyeOff toggle: keyed presence (`key="eye"` / `"eye-off"`) + `motion-pop-in`.
- Explicit judgment call (the task offered either `motion-pop-in` or a plain opacity/scale transition, "your call, document it"): kept `motion-pop-in`, for two reasons documented inline —
  1. Its overshoot is genuinely small in this system's tokens: `--motion-ease-spring: linear(0, 0.5 60%, 1.05 80%, 0.98 90%, 1)` peaks at **1.05**, not a dramatic bounce, so in practice it doesn't read as a "success celebration" on a mere visibility toggle.
  2. There's no clean sanctioned alternative: a plain CSS `transition` can't animate a value on the very frame a _keyed_ element remounts (nothing to interpolate from without `@starting-style`, which isn't part of this phase's motion vocabulary), and raw arbitrary `duration-[…]`/`ease-[…]`/`animate-[…]` are lint-banned. `motion-enter-up` was considered and rejected — it's a fade+4px-rise documented for _content_ arrival (chat messages, skeleton reveal); the rise reads oddly on a 16px inline icon.
- **Not touched:** the requirements-checklist per-row `Check`/`X` (met/unmet). The task's item 3 named only the Eye/EyeOff toggle; the checklist rows are a distinct swap surface not listed in the brief. Flagging it here as a candidate for a future pass rather than adding it unrequested.

### `split-button.tsx`

- **n/a — no source change.** `ChevronDown` is a static trigger icon (unconditionally rendered whenever `hasMenu` is true); it never changes based on `loading`/`disabled`/`variant`/`size`. The primary half's loading spinner is rendered inside `Button` (`packages/ui/registry/ui/button.tsx`), which is out of scope for this pass (another agent owns it) and isn't a swap within `split-button.tsx` itself. Added one regression test that locks in the "no swap" finding (chevron node identity is stable across a `loading` toggle, and carries no motion class) so a future change that accidentally introduces churn here gets caught.

### `input-clear`

- **n/a for all four files.** Checked `auto-save-input.tsx` and `password-input.tsx` for a clear/reset affordance — neither renders one. `auto-save-input`'s `X` is an _error status_ icon (not a clickable clear button); `password-input` only has the visibility toggle. No clear button exists to add motion to, and none was added (per instructions, not creating new UI).
