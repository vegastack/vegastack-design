# Phase M — feedback pack (notification-bell, badge, marker, message/bubble, skeleton, progress-indicator)

Scope: audit 09 §d3/d5/d6 + v4 mapping "badge pop / skeleton reveal". Canonical edits only
(`packages/ui/registry/ui/*`); `apps/docs` copy-in (`components/ui/*`) is **not** synced —
that requires `registry:build`, explicitly out of scope for this pass.

## 1. NotificationBell — unread badge pop (unconditional, not opt-in)

- Both badge modes (`dot` and count) now carry `motion-pop-in`.
- Dot mode needs no extra keying: the badge is already conditionally rendered
  (`hasUnread ? … : null`), so the false→true "new activity" transition is already a mount.
- Count mode: `<Badge key={displayCount} …>`. **Keyed on the DISPLAYED value, not the raw
  `count`** — a change from `count=150` to `count=200` (both render `"99+"`) does not replay
  the pop, because nothing visibly changed. Keying on the raw count would have fired a false
  "new activity" cue on every increment even once capped.
- This is the one component where the arrival animation is **not** opt-in — the badge only ever
  renders in direct response to a real state change, so there's no static-list case to guard
  against.
- Tests added: motion-pop-in class present (both modes), node identity changes across a
  count change that alters the display, node identity stays the SAME across a change that
  doesn't (150→200), and a rapid-fire sequence of count changes settles on the correct final
  value/accessible name without crashing.

## 2. Badge — `animateIn` (opt-in, default `false`)

- New boolean prop, applies `motion-pop-in` to the root when `true`. JSDoc explains the
  guardrail explicitly: badges in a static list (table column, filter-chip row) must not pop
  on every parent re-render/mount — only set it where the badge's own appearance IS the event
  (a status that just flipped, a freshly-applied label).
- Tests: default-off (no `motion-pop-in` class with no prop), on when passed.

## 3. Marker — `animateIn` (opt-in, default `false`, same name/mechanism as Badge)

- Same treatment: `motion-pop-in`, off by default. Marker is the chat-family's small label/status
  row (system notes, dividers), closer in size/role to Badge than to Message/Bubble, so it gets
  the pop-in vocabulary rather than enter-up.
- Tests: default-off / on.

## 4. Message + Bubble — `animateIn` (opt-in, default `false`, `motion-enter-up`)

- Added independently to **both** `Message` (the row) and `Bubble` (the surface) — they're
  separately composable primitives (a consumer might use one without the other), so each gets
  its own opt-in rather than forcing the animation through a shared ancestor. Consumers set
  either or both on a message they append after mount (streamed reply, just-sent message);
  default off so an existing transcript rendered on page load stays still.
  `MessageScroller` composes fine with it (no ownership conflict — it's a plain class on the row).
- Tests: default-off / on, for each component independently.

## 5. Skeleton reveal — `SkeletonReveal` (new flat export in `skeleton.tsx`)

Decision: implemented the small helper rather than leaving it purely as documentation, because
the "key both branches so the swap always remounts" detail is easy to get subtly wrong inline
(e.g. if a future edit made the loading and loaded branches both plain `<div>`s at the same tree
position, React would patch in place instead of remounting, silently killing the replay). A one-time
correct implementation is worth it here; it stays intentionally thin (~15 lines) and the docs still
lead with the inline one-liner as the "you don't need this" escape hatch.

- `Skeleton` itself is untouched — it stays the static placeholder, no motion added there.
- `SkeletonReveal({ loading, skeleton, children, ... })`: while `loading`, renders `skeleton`
  inside a keyed `React.Fragment` (no extra wrapper element); once `loading` is `false`, renders
  `children` inside a keyed `<div data-slot="skeleton-reveal-content" className="motion-enter-up">`.
  Fragment vs. `div` are different React element types at the same position regardless of keys, so
  the swap always unmounts/remounts on its own — the explicit `key="skeleton"`/`key="content"` is
  belt-and-suspenders documentation of intent, not strictly load-bearing today.
- `ref`/`className`/rest props apply to the content wrapper only — there's no host element to ref
  while loading (documented in the JSDoc).
- Tests: loading renders exactly the skeleton prop with no extra wrapper; loaded renders the
  wrapper with `motion-enter-up`; the content node remounts across a loading→loaded transition;
  className merge; ref forwarding; a11y in both states.

## 6. ProgressIndicator — value sweep

- Read the component before touching it, per the task's own instruction: the arc is driven by
  `stroke-dasharray` on the fill `<circle>` (constant `circumference`, growing `dash`), **not**
  `stroke-dashoffset`. Added
  `transition-[stroke-dasharray] duration-base ease-standard motion-reduce:transition-none` to
  that circle only — mirrors the linear `Progress` bar's own `transition-[width]
duration-base ease-standard`.
- The track outline (and the squircle `<rect>`) never carry `stroke-dasharray`, which makes
  `circle[stroke-dasharray]` a stable, non-invasive test selector for "the fill arc" without
  adding a new `data-slot` (house rule: data-slots unchanged).
- At `value=0` the fill circle is still conditionally unmounted (`percent > 0 &&`), so a drop to
  zero snaps away rather than sweeping down — pre-existing behavior, left as-is (out of the
  audit's ask, and arguably correct: there's nothing to sweep to).
- Tests: className-based check (arbitrary Tailwind isn't compiled in this test harness, so this
  pins intent even without real CSS) + a **computed-style** test using the style-mirror technique
  from `checkbox.test.tsx`'s "Touch-target remediation" section — injects a literal `<style>` that
  mirrors exactly what `transition-[stroke-dasharray] duration-base ease-standard` compiles to
  (`200ms` / `cubic-bezier(0.2, 0, 0, 1)`, read from `packages/tokens/dist/theme.css`), keyed to
  the fill-arc selector, then asserts the real `getComputedStyle()` result. Also pinned: the track
  selector stays unambiguous (exactly one `circle[stroke-dasharray]` per render, any shape), and
  the fill arc is absent at `value=0`.
