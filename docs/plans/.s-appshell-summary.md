# Phase S — App Shell (audit 11 §c/§d) — summary

Scope: new `packages/ui/registry/ui/app-shell.tsx` + `app-shell.test.tsx`, new
`apps/docs/components/preview/app-shell.tsx`, new
`apps/docs/content/docs/components/app-shell.mdx`. `sidebar.tsx`, `page-header.tsx`,
`breadcrumb.tsx` were read in full (per instructions) but not touched.

## API surface

Five exports, all in `app-shell.tsx`, no `'use client'` anywhere in the file (see "Server-safety"
below):

- **`AppShell`** — root. Wraps `SidebarProvider`, forwarding `defaultOpen` / `open` /
  `onOpenChange` / `mobileBreakpoint` / `keyboardShortcut`. Renders the skip-to-content link
  (`sr-only focus:not-sr-only`, `href="#main-content"`, token-styled when visible) as the first
  child, then `children`.
- **`AppShellSidebar`** — thin wrapper over `Sidebar`: defaults `aria-label="Main navigation"`,
  passes `variant`/`collapsible`/`side`/everything else through unchanged.
- **`AppShellHeader`** — `<header>` (banner): `SidebarTrigger` (always visible) + `min-w-0
  flex-1` middle slot (`children`) + `shrink-0` `actions` slot.
- **`AppShellContent`** — `<main id="main-content" tabIndex={-1}>`, `@container/app-shell-content`,
  `flex-1 min-h-0 overflow-y-auto`. Takes a `variant` prop (`'sidebar' | 'floating' | 'inset'`,
  default `'sidebar'`) for its own inset panel treatment.
- **`AppShellSkeleton`** — sidebar column (logo circle + N `SidebarMenuSkeleton` rows) + header
  line + content region (stat-card row + tall rect), `navItemCount`/`statCardCount` props.

`data-slot` values: `app-shell`, `app-shell-skip-link`, `app-shell-sidebar`, `app-shell-header`
(+ `app-shell-header-middle`/`app-shell-header-actions`), `app-shell-content`,
`app-shell-skeleton`.

## Decisions (with rationale)

1. **No extra wrapper `<div>` in `AppShell`.** `SidebarProviderProps` already extends
   `React.ComponentProps<'div'>` and spreads extra props (incl. `className`/`data-slot`) onto its
   own internal `sidebar-wrapper` div (`sidebar.tsx`, already `flex min-h-svh w-full` — exactly
   the row a shell needs). `AppShell` reuses that element, overriding its `data-slot` from
   `"sidebar-wrapper"` to `"app-shell"` via the same last-spread-wins JSX pattern
   `AppShellSidebar` uses on `Sidebar` — rather than nesting a second flex row around it. Verified
   in `app-shell.test.tsx`: `[data-slot="app-shell"]` exists, `[data-slot="sidebar-wrapper"]`
   does not.

2. **No `AppShellBody`/content-column component — deliberate, documented in both the JSDoc and
   the mdx.** The audit's file manifest sketch only lists five parts (no column wrapper), and
   there's a structural reason not to invent one: `AppShellHeader`'s `<header>` only keeps its
   `banner` ARIA role while it's NOT a descendant of `<main>`/`<article>`/`<aside>`/`<nav>`/
   `<section>`. That means `AppShellHeader` and `AppShellContent` must stay TRUE SIBLINGS. A
   component that owned both inside one wrapper would tempt collapsing them into one JSX
   subtree where accidentally nesting header inside main becomes easy. The plain
   `<div className="flex h-svh min-w-0 flex-1 flex-col">` shown in every usage example is the
   full extent of that "column" — it's a documented convention, not new API surface.

3. **`AppShellContent` does NOT pair with `SidebarInset` — takes an explicit `variant` prop
   instead. This is the one real deviation from audit 11 §c's literal suggestion** ("`AppShellContent`
   … wraps children in `ScrollArea` … `SidebarInset`" wasn't literally proposed for content, but
   `sidebar.tsx`'s own JSDoc says "pair `variant='inset'` with `SidebarInset` on the main
   content"). Investigated and rejected: `SidebarInset` (`sidebar.tsx`) itself renders a `<main>`.
   Composing it as `AppShellContent`'s wrapper would produce a SECOND `<main>` landmark, and
   `SidebarInset`'s panel styling works via `md:peer-data-[variant=inset]:…` — a plain CSS sibling
   selector that only matches a DIRECT sibling of `Sidebar`'s `<nav>` in the same parent. Since
   `AppShellContent` can't be that direct sibling (decision #2 — `AppShellHeader` needs to sit
   between them for the banner landmark to work), the peer selector would silently never fire.
   Resolution: `AppShellContent` takes an explicit `variant` prop and applies the SAME classes
   `SidebarInset` would (`md:m-2 md:ml-0 md:rounded-lg md:border md:border-border
   md:shadow-overlay`) directly, no CSS peer trickery, no second `<main>`. Consumers pass the same
   `variant` to `AppShellSidebar` and `AppShellContent`. `SidebarInset` remains fully correct and
   untouched for its own standalone use case (composing `Sidebar` directly, without `AppShell`).
   Tested: `AppShellContent variant="inset"` carries `md:rounded-lg`/`md:border`; the default
   (`variant="sidebar"`) doesn't.

4. **Scroll: plain `overflow-y-auto`, not `ScrollArea` — the audit's own "judgment" call, taken.**
   Beyond the audit's stated reasons (simpler `<main>`, native scroll-restoration), there's a
   second reason specific to this shell: `ScrollArea`'s `Viewport` is itself a second
   `tabIndex={0}` scrollable landmark nested inside `<main>` — that would sit awkwardly next to
   the skip link's own `tabIndex={-1}` focus target on the SAME element. Plain `overflow-y-auto`
   avoids that. `AppShellContent` doesn't force a bounded height either — it's `flex-1 min-h-0`,
   so it scrolls internally only when the ancestor chain bounds it (the `flex h-svh flex-col`
   column shown everywhere); undecorated, it's simply inert and the whole page scrolls instead.
   Both are documented as valid.

5. **`AppShellSkeleton` stays server-safe by directly composing `SidebarMenuSkeleton`** (from
   `sidebar.tsx`, a `'use client'` module) rather than duplicating its markup with raw `Skeleton`
   parts. Resolved the audit's open question ("check; if so, either build … or accept and
   document") by applying the actual RSC rule correctly: a Server Component MAY import and render
   a Client Component as JSX without itself crossing the client boundary — only the DECLARING
   module (`sidebar.tsx`) is a client boundary; `app-shell.tsx` never gains one. Confirmed
   `SidebarMenuSkeleton` itself has zero hooks/client-only logic, so this isn't even borderline.
   `app-shell.tsx` carries no `'use client'` directive anywhere — every interactive leaf
   (`SidebarProvider`, `Sidebar`, `SidebarTrigger`, `SidebarMenuSkeleton`) already lives, and is
   already marked, inside `sidebar.tsx`.

6. **`AppShellSidebar` and `AppShellContent` re-stamp `data-slot`** on the element they wrap
   (`"sidebar"` → `"app-shell-sidebar"`; `AppShellContent` gets its own literal `data-slot`, no
   collision since it's not wrapping another component). This is a deliberate, minor DOM
   attribute change from the underlying `Sidebar` output — intentional so shell-level
   tests/styling can target the shell's parts distinctly from a bare `Sidebar` used outside
   `AppShell`. `Sidebar`'s other data attributes (`data-state`/`data-collapsible`/`data-variant`/
   `data-side`) are untouched.

```json
  "categories": ["layout"],
  "dependencies": [
    "@vegastack/utils@^0.1.0",
    "@vegastack/tokens@^0.1.0"

    "@vegastack/sidebar",
    "@vegastack/skeleton"
  ],
  "files": [
    {
      "path": "packages/ui/registry/ui/app-shell.tsx",
      "type": "registry:ui",
      "target": "@ui/app-shell.tsx"
    }
  ],
  "meta": {
    "whenToUse": "The root layout for a dashboard/console app — sidebar + header + main content, shared across every downstream VegaStack app.",
    "whenNotToUse": "A marketing/docs page with no persistent nav rail, or an app that already owns an equivalent shell — compose Sidebar/PageHeader/Breadcrumb directly instead.",

```

No `@base-ui/react` / `lucide-react` / `class-variance-authority` direct `dependencies` —
`app-shell.tsx` imports only `cn` (`@vegastack/utils`) plus `Sidebar`/`SidebarMenuSkeleton`/
`SidebarProvider`/`SidebarTrigger` (from the `sidebar` registry item, which brings its own npm
deps transitively) and `Skeleton` (from the `skeleton` item). No `scroll-area` dependency — see
decision #4 (deliberately not used).

## preview/index.tsx (not applied — forbidden file)

Add one barrel line, alongside the existing `sidebar`/`page-header` exports:

```ts
export * from './app-shell';
```

Without this line, `apps/docs/components/preview/app-shell.tsx`'s exports
(`appShellDemo`/`appShellInset`/`appShellFloating`/`appShellSkeletonDemo`) exist and are correctly
imported by the new mdx's `<ComponentPreview>` tags, but the docs site's preview scanner (which
reads the barrel) won't pick them up until this line is added — flagging as a required follow-up
alongside the `registry.json`/`meta.json` edits above.

## Test evidence (from `packages/ui`)

`npx tsc --noEmit`: clean.

`npx vitest run registry/ui/app-shell.test.tsx`: **19/19 passed**, no retry needed. Copied
`sidebar.test.tsx`'s scoped `beforeEach`/`afterEach` `matchMedia`-desktop-default harness
(this suite's real Playwright viewport is 414×896 — same mobile-default hazard).

Coverage:
- Landmark trio (banner/navigation/main) + exactly one `<main>` in the DOM.
- Skip link is the first Tab stop; activating it (`.click()`) moves `document.activeElement` to
  `#main-content`.
- Header: trigger present, `actions` slot renders (and is entirely absent when omitted), middle
  slot carries `min-w-0` and shows `children`.
- `AppShellContent`: `#main-content` id + `tabIndex={-1}`, `@container/app-shell-content` class
  present; `variant="inset"` adds the panel classes, default `variant="sidebar"` doesn't.
- `data-slot` overrides: `app-shell` present or `sidebar-wrapper` absent; `app-shell-sidebar`
  present on the `<nav>`; `aria-label` default + override.
- `AppShell` forwards `defaultOpen`, the Cmd/Ctrl+B shortcut works through the wrapper, and
  `keyboardShortcut={false}` disables it.
- `AppShellSkeleton`: `aria-hidden`/`aria-busy`, `navItemCount`/`statCardCount` produce the
  matching placeholder counts, and two independent renders produce byte-identical width classes
  (deterministic, no `Math.random()`).
- `expectNoA11yViolations`: desktop, mobile-mocked (sheet closed), mobile-mocked (sheet open,
  audited against `document.body` since the sheet portals there).

`node ../../tooling/design-lint.mjs registry`: clean.
