## Why the pattern deviates for FilterChip's remove button

Every other target uses the standard invisible `::before` hit-area expansion
(`relative` on the interactive element + `before:absolute before:-inset-*`,
transparent generated content). I initially applied the same pattern to the
FilterChip remove `<Button>`, but discovered — by hand, with a real Chromium
instance (`vitest-browser-react` + Playwright), not by assumption — that it
does not work for that target:

- Tailwind's own Preflight sets `button, input[type=button|reset|submit],
::file-selector-button { appearance: button }`.
- A native-appearance `<button>` clips its own overflowing generated content
  (`::before`/`::after`) to its border box **once nested a couple of levels
  deep** in Chromium. `getComputedStyle(button, '::before')` still reports
  the correct resolved `inset`/`width`/`height` (so a naive "does the CSS
  compute right" check would pass), but `document.elementFromPoint()` at any
  point outside the visible 20px box never resolves to the button or its
  pseudo — the expansion is real in the CSSOM but unreachable by a pointer.
- The same markup with a `<span>` at the identical nesting depth is **not**
  clipped (verified side-by-side) — this is button-specific, not a general
  pseudo-element/nesting limitation.
- `appearance: none` fixes it only when the button is the literal render
  root (no wrapping element); once nested inside even one more `<div>` (the
  real FilterChip's actual structure), clipping persists regardless of
  `appearance`.

Given a pseudo-element is unreliable for this specific native-control case,
the fix instead grows the button's **real** border-box from `size-5` (20px)
to `size-6` (24px), with compensating margins (`ml-0.5`→`0`, `-mr-0.5`→
`-mr-1`) so the button's visual footprint inside the chip — and the × glyph's
centered position within it (`items-center justify-center`, unaffected by
the bigger box) — is byte-for-byte identical to before (both resolve to a
28px total span consumed between the value text and the chip's own edge).
No pseudo-element is involved, so the Chromium clipping bug is sidestepped
entirely rather than worked around.

## Test evidence

All six `.test.tsx` files gained a "Touch-target remediation (WCAG 2.5.8)"
section. This test harness runs `vitest run` in real Chromium via Playwright
but with **no compiled Tailwind** (only `test/contrast.css`, a file outside
this task's scope, compiles real Tailwind) — confirmed by direct probing:
`getComputedStyle` on a freshly-rendered `size-4`/`before:-inset-1` element
returns `position: static`, zero size, `content: none`. Every existing test
in these files already documents this same limitation for click handlers.

To still get **real, browser-measured** geometry (not hand-rolled arithmetic
assuming Tailwind compiled correctly), each new test:

1. Injects a literal `<style>` tag that is a 1:1, mechanical mirror of what
   the exact Tailwind utility values used in the component compile to (the
   `-inset-1 = 4px` scale given in this task's house rules), keyed to the
   component's own `data-slot`/`data-size` attributes (real regardless of
   compiled CSS).
2. Reads `getComputedStyle(el, '::before').width/height` — confirmed by
   direct experiment that Chromium resolves these to real used-value pixels
   (not the `auto` keyword) once all four `inset` sides are set — and asserts
   `>= 24` in both dimensions.
3. Uses `document.elementFromPoint()` at a coordinate just outside the old
   visual box but inside the new expanded boundary, asserts it resolves to
   the control, then fires a real click on the resolved element and asserts
   the expected state change (`onCheckedChange`, `onValueChange`,
   `onSelectionChange`, `onRemove`, or focus reaching the slider's hidden
   range input, since a bare click doesn't "toggle" a drag handle).
4. A companion test also probes a coordinate just _beyond_ the expanded
   boundary and asserts it does **not** resolve to the control, to prove the
   expansion is bounded, not accidentally unbounded.

One real timing flake was found and hardened against: `getComputedStyle`
occasionally read `auto` for a freshly-styled pseudo-element on the very
first read after `render()`. A forced synchronous layout flush
(`el.getBoundingClientRect()`) immediately before every `getComputedStyle`
read eliminates it (added to every affected test, all 6 files).

## Visual-regression risk

None identified. Every fix is either a fully invisible generated
pseudo-element (no background, no border, `content: ''`) or, for the
FilterChip remove button, a real-box growth with margins mathematically
compensated to keep the total consumed layout space and the icon's centered
position identical (verified by hand-arithmetic in the code comment, not
just asserted). No visible size, color, spacing, or icon glyph size changed
in any of the six files. `design-lint` (which enforces semantic-token-only
usage) is clean on the whole `registry` directory. VRT itself was
intentionally **not** run, per this task's explicit scope (another agent
covers it).
