# Phase D — preview UX: copy-as-prompt, responsive frame, per-preview theme decision, playground

Scope: `apps/docs/components/component-preview.tsx` (edited), new files under `apps/docs/components/**`
(`copy-prompt.tsx`, `preview-controls.tsx`, `playground.tsx`, `button-playground.tsx`),
`apps/docs/components/mdx.tsx` (additive registration only), one demo adoption in
`apps/docs/content/docs/components/button.mdx`. Did not touch `apps/docs/app/**`,
`apps/docs/public/**`, `packages/**`, `tooling/**`, any `package.json`, the VRT spec, Playwright
config, or restructure `apps/docs/components/preview/index.tsx` (no preview demos were added there
— the playground isn't a `<ComponentPreview>` demo, see §4).

## 1. Copy-as-prompt — shipped

Investigated the existing "Copy Markdown" affordance first: `apps/docs/app/docs/[[...slug]]/page.tsx`
renders fumadocs-ui's `MarkdownCopyButton` (`fumadocs-ui/dist/layouts/shared/page-actions.js`), which
`fetch()`es a pre-rendered `.md` sibling route at runtime and writes it to the clipboard —
`markdownUrl` comes from `getPageMarkdownUrl(page)` in `apps/docs/lib/source.ts`
(`${docsContentRoute}/${slug}/content.md` → `/llms.mdx/docs/<slug>/content.md`, served by
`apps/docs/app/llms.mdx/docs/[[...slug]]/route.ts`, statically generated under `output: 'export'`).
That confirmed the brief's suggested mechanism (client fetch of a static `.txt`/`.md` sibling route)
is exactly what the house pattern already does — so `CopyPromptButton` reuses it rather than reading
anything from disk at runtime.

**Cannot sit "next to" `MarkdownCopyButton` literally** — that button lives in `app/docs/[[...slug]]/page.tsx`,
which is `apps/docs/app/**` and out of scope for this phase (owned by the parallel `main`/SEO agent).
Shipped instead as a toolbar button on every `<ComponentPreview>` block (`apps/docs/components/component-preview.tsx`,
a legal edit target) — this is the "whatever ComponentPreview-level changes apply to ALL pages
automatically" mechanism the brief explicitly sanctioned as an alternative.

- `apps/docs/components/copy-prompt.tsx` — `CopyPromptButton({ componentName, displayName? })`.
  Fetches `content.md` for the *current* page via `usePathname()` (`fumadocs-core/framework`,
  already used elsewhere in fumadocs-ui internals; the docs app root is wrapped in fumadocs'
  `RootProvider`, which supplies the required `FrameworkProvider` — verified this resolves at
  runtime, no new provider needed), composes `"Use the VegaStack <Name> component… [install cmd]
  … [usage/full markdown]"`, and writes it to the clipboard. Module-level `Map` cache keyed by the
  markdown URL, mirroring fumadocs' own `MarkdownCopyButton` cache. `Button` (outline/sm) +
  `Sparkles`/`Check` icon swap + `sonner` toast on success/failure — same idiom as the registry's
  own `CopyButton` (`components/ui/copy-button.tsx`).
- **Scoping the install command**: `component-preview.tsx` only shows the button when `file` matches
  `components/preview/<name>.tsx` *and* `packages/ui/registry/ui/<name>.tsx` actually exists
  (`existsSync`, same cwd `readFileSync(file, …)` already relies on). This is what filters out the
  handful of preview files that aren't a single installable registry component — `utilities.tsx`
  (shimmer/scroll-fade demos), `wrapper.tsx`, and the `dashboard-01` block page (different `file`
  path entirely) — so "Copy Prompt" never advertises a `shadcn add @vegastack/utilities` that
  doesn't exist. Verified: every other `components/preview/*.tsx` basename has a matching
  `packages/ui/registry/ui/*.tsx` (diffed the two directory listings).
- **Known limitation, stated plainly**: a page with several `<ComponentPreview>` blocks for the same
  component (Button's Variants/Sizes/States/Matrix — 4 blocks, same `file`) shows the toolbar 4
  times, not once. Deduplicating "once per page" would need either (a) page-level state threaded
  from `app/docs/[[...slug]]/page.tsx` (forbidden) or (b) module-scoped mutable state in the RSC
  render (unsafe across concurrent page renders in the same worker). Accepted as the honest
  trade-off of the toolbar living in `component-preview.tsx` instead of `page.tsx`.
- Manually verified in the dev server (`/docs/components/button`): the fetch (`GET
  /llms.mdx/docs/components/button/content.md` → 200), clipboard write, and the
  `"Button prompt copied — paste it into your AI assistant"` toast all fire correctly on click.

## 2. Responsive-frame toggle — shipped, container-query framing

`apps/docs/components/preview-controls.tsx`:
- `PreviewControlsProvider` — client Context holding `width: 'mobile' | 'tablet' | 'full'`
  (`useState`, default `'full'`). Wraps the *entire* `<Tabs>` tree in `component-preview.tsx` so the
  two consumers below — separate subtrees under the same `<Tabs>` (the `label` slot vs. the `Tab`
  content) — share one source of truth without lifting state into `app/**`.
- `FrameWidthToggle` — a `ToggleGroup`/`ToggleGroupItem` trio (`Smartphone`/`Tablet`/`Monitor`
  icons, `aria-label`s, no separate `Tooltip` — matches the existing icon-only `ToggleGroupItem`
  convention in `components/preview/toggle-group.tsx`), rendered in the `Tabs` `label` slot
  (`fumadocs-ui/components/tabs`'s `label` prop renders a `me-auto` span before the tab triggers —
  confirmed by reading `fumadocs-ui/dist/components/tabs.js`; it's the only extensibility point the
  component exposes, so the toolbar sits left of Preview/Code rather than literally "beside" them).
- `PreviewFrameContainer` — wraps the demo, applies a `max-w-[375px]` / `max-w-[768px]` / `max-w-none`
  class (never an inline `style` with a direct visual property — the design-system's `§7.1`
  inline-style contract in `tooling/design-lint.mjs` bans that; confirmed `design-lint.mjs` doesn't
  even scan `apps/docs/components/**` today, but followed the contract anyway), centered,
  `overflow-x-auto` so a demo wider than the frame scrolls inside it instead of breaking page layout,
  with a dashed border only when constrained (visual frame edge).
- **iframe isolation evaluated and rejected for this mechanism** (see also §3): it would need a
  static route under `app/**`, which is forbidden here. The container-width toggle is the mechanism
  that fits inside the allowed file set.
- **Honest limitation, written into the `FrameWidthToggle` doc comment**: this narrows a CSS
  container, not the browser viewport — `@media` breakpoints never fire from it. Checked which
  ComponentPreview demos are actually built on this design system's Tailwind v4 `@container`
  shell-layout convention (Phase R/S): `AppShellContent` (`@container/app-shell-content`,
  `components/ui/app-shell.tsx`, demoed in `components/preview/app-shell.tsx`) and `SettingsRow`
  (`@container/settings-row`, `components/ui/settings-row.tsx`, demoed in
  `components/preview/settings-row.tsx`) — these two visibly reflow under the toggle.
  `Field`'s `orientation="responsive"` (`@container/field-group`) is container-query-capable by the
  same mechanism but **has no live ComponentPreview demo currently** (grepped
  `components/preview/field.tsx` — no `orientation="responsive"` usage exists yet), so it won't
  visibly respond even though the underlying component would. Every other demo keeps its normal
  layout regardless of the selected preset; genuine viewport-media-query breakpoints still need a
  real browser resize.
- Manually verified: toggling to "Mobile width, 375 pixels" on Button's Variants block visibly
  reflows the button grid into a narrow column inside a dashed frame; "Full width" restores the
  original unconstrained layout exactly (pixel-identical to pre-change — deterministic default).

## 3. Per-preview theme (CX-15) — DEFERRED, as sanctioned

Investigated the clean-scoped-mechanism escape hatch the brief pointed at: Base UI's `Portal`
`container` prop. Checked `@base-ui/react`'s `Select`/`Dialog`/`Popover`/`Tooltip`/`DropdownMenu`
wrappers in `apps/docs/components/ui/*.tsx` — none of them expose a `container`/`portalProps.container`
override that a per-preview theme wrapper could point at a scoped node; every one either omits the
prop entirely from its own `*ContentProps` (e.g. `SelectContentProps.positionerProps` forwards to
`Positioner`, not `Portal`) or hardcodes `<BaseX.Portal>` with no prop passthrough at all. Plumbing
it through would mean editing every registry primitive with a portaled part — `packages/**`, out of
scope for this phase and a real component-API change, not a docs-infra one.

Without that, a scoped `.dark` wrapper around one `<ComponentPreview>` breaks exactly as CX-15
predicts: the trigger (inside the scoped wrapper) themes correctly, but any portaled popup content
(Select/Dialog/DropdownMenu/Tooltip/HoverCard/Sheet — all portal to `document.body` per Base UI's
default) renders under the PAGE's theme, not the preview's, producing a visibly split-themed demo the
moment a reader opens a popup.

**Decision: defer**, per the brief's explicit sanction ("CX-15 explicitly sanctions deferral"). The
existing global theme toggle (fumadocs' `RootProvider` + `next-themes`, in the sidebar) already lets a
reader view every demo — including popovers — in a fully consistent light or dark page. A per-preview
toggle without iframe isolation would be strictly worse (half-themed popups) than not having one.
Iframe isolation would fix it cleanly but needs a static route under `apps/docs/app/**`, forbidden in
this phase's file scope; flagging it as the concrete follow-up (`docs/plans/` — a future phase with
`app/**` in scope should revisit: an isolated `/preview/<name>` iframe route would solve per-preview
theme AND make the responsive-frame toggle a real viewport instead of a container, in one move).

## 4. Props playground — shipped, Button only, generalized API

- `apps/docs/components/playground.tsx` — generic `PropsPlayground<Keys extends string>`, driven by
  a declarative `PlaygroundConfig<Keys>`: `controls` (`{ type: 'select' | 'switch', key, label,
  defaultValue, options? }`), `render(state)`, `toCode(state)`. Controls compose `Field` + `Select`
  (for `'select'`) or `Field` + `Switch` (for `'switch'`) — the same `<Field label=… orientation=
  "horizontal"><Switch/></Field>` / `<Field label=…><Select/></Field>` pairing already used
  throughout `components/preview/switch.tsx` and `components/preview/field.tsx`. Generated JSX
  renders in a plain `<pre><code>` (not fumadocs' Shiki `CodeBlock` — that needs an async
  server-side `highlight()` call; this is a client component with dynamic per-keystroke content) with
  a `CopyButton` (reused straight from `components/ui/copy-button.tsx`) to copy the snippet.
  Deterministic initial state: every field's `defaultValue`, so a fresh page load — and VRT — is
  stable; nothing changes until a reader touches a control.
- `apps/docs/components/button-playground.tsx` — the Button-specific `PlaygroundConfig`: `variant`
  (10 options, all of `buttonVariants`'s `variant` union), `size` (`xs`/`sm`/`default`/`lg`),
  `disabled` and `loading` switches. `toCode` omits default-valued props from the generated snippet
  (`<Button>Save changes</Button>` at rest, `<Button variant="destructive">Save changes</Button>`
  once changed) so the snippet reads the way a human would actually write it.
- **Generalization path** (asked for explicitly): adding a second playground is "write a new
  `PlaygroundConfig`, export a thin wrapper component, register it in `mdx.tsx`, drop
  `<XPlayground/>` into `x.mdx`" — zero changes to `playground.tsx` itself. `button-playground.tsx`
  is the template to copy.
- Adopted in `apps/docs/content/docs/components/button.mdx` — new `## Playground` section between
  `## Usage` and `## Variants`, per the task's "ONE demo adoption" instruction.
- Manually verified in the dev server: changing Variant to "Destructive" live-updates both the
  rendered `Button` and the generated `<Button variant="destructive">Save changes</Button>` snippet
  instantly; the copy button on the snippet works.

## VRT impact — say so explicitly

`component-preview.tsx` changes are **global** — every page using `<ComponentPreview>` (the vast
majority of `content/docs/components/*.mdx` + several `content/docs/blocks|utilities/*.mdx`, ~88
pages) now renders a toolbar row (frame-width toggle, plus Copy Prompt where a registry component
name resolves) above the Preview/Code tabs, and the Preview tab content is wrapped in an extra
`PreviewFrameContainer` div. Every one of those pages' baselines will need re-capturing — expected
and unavoidable for a shell-level change; per the task brief, VRT re-baselining is the orchestrator's
job, not run here. `content/docs/components/button.mdx` additionally gains a whole new `## Playground`
section, a bigger diff for that one page specifically.
